Lesson 6

Reading Errors & Debugging

Debugging means cutting the search space in half, then in half again, until only one thing is left. This lesson gives you the three tools for doing that.

25 min Beginner Phase 1 · Foundations

Your goal

1 Why this matters

Isolate the problem

When a mechanism doesn't move, three sub-teams each have an opinion. Software says it's wiring. Electrical says it's code. Build says it's definitely not build. That argument can burn an entire meeting.

The team settles it with a procedure: open the vendor's hardware client and apply a test voltage directly to the motor, with no robot code involved at all.

  • Motor spins → wiring and hardware are fine. It's code.
  • Motor doesn't spin → it was never going to be code.

One test rules out half the possibilities.

That's what debugging is: halving the search space until only one thing is left.

The same team once spent two full days hunting a bug that turned out to be a single number set too high. Two days is what it costs when you search by staring instead of by halving.

2 Three kinds of wrong

They are not equally expensive, and the rest of this lesson builds on this table.

Compiler error
Found before it ever runs. Tells you the file, the line, and usually the exact character. Costs minutes.
Runtime error (an exception)
Found while it's running, and it stops. Tells you the type, a message, and the line it died on. Costs minutes to hours.
Logic error
Found never, unless you notice. Tells you nothing at all. Costs the two days.

A compiler error is the best news you can get.

It's the computer refusing to let you make a mistake, for free, before anything moves. The error you should be afraid of is the one that produces no error.

Red squiggle vs yellow squiggle

Red = an error; the code will not build. Yellow = a warning, usually something declared and never used. It's annoying but it won't stop the build. Learn to tell them apart at a glance; you'll see both constantly in Phase 2.

3 Anatomy of a compiler error

Every compiler error has four parts. Learn them once and you can read all of them.

compiler output
Main.java:3: error: ';' expected
        int canId = 2
                     ^
1 error
Main.java
Which file.
:3
Which line. Start here.
error:
This is fatal, not a warning.
';' expected
What the compiler wanted and didn't get.
^
The exact character it gave up at.
When the named line looks fine, check the line above

The caret points at where the compiler noticed, which is often just past where you went wrong. A missing semicolon on line 3 is frequently reported at line 4, because the compiler kept reading, hoping.

4 The four you'll actually see

(a) ';' expected: the missing semicolon. Add the ;. Note the caret sits at the end of the previous line's content.

error
Main.java:3: error: ';' expected
        int canId = 2
                     ^

(b) cannot find symbol: a name Java has never heard of. This is the typo error, and Java tells you exactly which name it looked for.

error
Main.java:4: error: cannot find symbol
        System.out.println(canID);
                           ^
  symbol:   variable canID
  location: class Main

canId was declared; canID was used. One capital letter. The same message appears when you misspell a method, forget to declare a variable at all, or write string instead of String.

(c) incompatible types: the wrong shape of thing. The message names both types and which direction the problem runs.

error
Main.java:3: error: incompatible types: possible lossy conversion from double to int
        int ticks = 4.0;
                    ^

“Lossy” means something would have to be thrown away, and Java refuses to do that behind your back.

(d) reached end of file while parsing: a missing }. This one lies about location: it always points at the last line, because that's where the compiler finally ran out of file still waiting for a closing brace. Count your braces.

5 Fix the first error first

One missing semicolon can produce fifteen errors, because everything after it confused the parser. Students delete code in a panic. Don't.

Fix the topmost error, recompile, and look again.

Very often fourteen of the fifteen were never real. You'll see this happen for yourself in this lesson's project.

6 Stack traces

An exception is the program hitting something impossible while running and stopping, rather than continuing with nonsense. Java prints a stack trace:

console
Reading sensors...
Exception in thread "main" java.lang.ArithmeticException: / by zero
        at Main.main(Main.java:6)

Read it in three moves:

  1. What type? ArithmeticException, a maths problem.
  2. What message? / by zero, so you divided by zero.
  3. Where? Main.java:6, which is the file, then line 6.

Notice the first line: Reading sensors... did print. Everything before the crash ran normally, so the output before the crash shows you how far it got.

Find your own file name in the trace

A real stack trace can be a dozen at ... lines deep, most of them inside Java's own code. The line you care about is the one with your file name in it, here Main.java. Unit J3 explains why the list exists at all.

The three you'll hit first:

100 / 0 with two ints
ArithmeticException: / by zero
"Penguin".charAt(7)
StringIndexOutOfBoundsException: Index 7 out of bounds for length 7
.length() on a null String
NullPointerException. The box is empty, so there's no thing there to ask. Unit J4 gives this its own lesson.

The exception type is a category; the message is the specifics. After ten of these you'll read Index 7 out of bounds for length 7 and know the answer before you've found the line.

7 The error with no error message

Here's a program that compiles cleanly, runs cleanly, and lies to you:

Main.java Java 
int encoderTicks = 90;
int ticksPerRotation = 20;
double rotations = encoderTicks / ticksPerRotation;   // both int - the .5 is discarded
double degrees = rotations * 360;
System.out.println("Arm is at " + degrees + " degrees");
output
Arm is at 1440.0 degrees

The right answer is 1620.0. 90 ÷ 20 is 4.5 rotations, and 4.5 × 360 is 1620. The program said 1440 because 90 / 20 is integer division, the same silent-zero problem from the operators lesson.

Nothing on your screen is red. On a real robot, this arm stops 180° short and everyone blames the encoder.

8 Print debugging

You can't see inside a running program, so you make it tell you what it's doing. Put a println after every step that produces a value, and label every one.

  1. Label them. A bare 4.0 in the console is worthless. DEBUG rotations = 4.0 is an answer.
  2. Print the inputs too, not just the output. Half the time the bug is that an input isn't what you assumed.
  3. Print early, print often, delete afterwards. Debug prints are scaffolding.
output
DEBUG encoderTicks    = 90        <- correct
DEBUG ticksPerRotation= 20        <- correct
DEBUG rotations       = 4.0       <- WRONG, should be 4.5
DEBUG degrees         = 1440.0

Two correct inputs and a wrong output means the bug is on the line between them. You found it by halving the search, the same move as applying a test voltage.

The fix is one line:

Main.javaJava
double rotations = (double) encoderTicks / ticksPerRotation;   // now 4.5

9 The checklist

Come back to this all season.

  1. Read the message. Out loud if necessary. Most of them say exactly what is wrong.
  2. Go to the line it names. If that line looks perfect, check the line above.
  3. Fix one thing. Re-run. Never change three things at once, or you can't tell which one helped.
  4. If there's no message, make one. Add labelled prints and find the first value that isn't what you expected.
  5. Halve the search. Known-good above, known-bad below: the bug is between them.
  6. Say it to a person. Describing the bug out loud finds an astonishing number of bugs before the other person has spoken.
“One change, one run” is a Phase 2 rule too

When you tune a PID controller in Unit 6, the formal rule is change one variable at a time, for exactly this reason. Change two and the result tells you nothing.

Everyone gets errors

Everybody on this team gets errors every single meeting. Experienced programmers cause plenty of errors too. They just take a few seconds to read one.

10 Run it yourself

Run it once. It works. Now break it, one change at a time, and read the message before you undo it.

Undo before the next one

Two breaks at once and you can't tell which message came from which. It's the same mistake as changing two PID gains at once.

Check your four messages against these
the four messages
1.  Main.java:3: error: ';' expected

2.  Main.java:5: error: cannot find symbol
      symbol:   variable canID

3.  Main.java:3: error: incompatible types: int cannot be converted to String

4.  Main.java:N: error: reached end of file while parsing

Number 4 points at the last line of the file, not at the brace you deleted. That's the misleading error from section 4.

12 Common misconceptions

Get these out of the way
  • “An error means I'm bad at this.” It means the compiler is doing its job. The only variable is how fast you read them.
  • “Fifteen errors means fifteen problems.” Usually one problem and fourteen consequences. Fix the top one and recompile before you believe the rest.
  • “The line number is always where the mistake is.” It's where the compiler noticed. For missing semicolons and braces, the mistake is usually earlier.
  • “If it runs, it's right.” 1440.0 ran perfectly. Running and being correct are unrelated properties.
  • “I should read the whole stack trace.” Read the first line and the first at line containing your file. The rest is Java's plumbing.
  • “Print debugging is what you do when you don't know the real tools.” It's a real tool, and on a robot forty feet away with no debugger attached, it's often the only one.
  • “I'll just change a few things and see.” Change one thing, run, look. Otherwise you learn nothing from the result.
Mini-project

The Broken Startup Report

Someone left a status report in the repo that doesn't build. Once it builds, it prints a wrong number. Get it working, then get it correct.

  1. Make it compile. There are three compiler errors. Fix the first one, re-run, and only then look at what's left. Note each message you see.
  2. Make it correct. Once it runs, one printed number is wrong. Find it with labelled DEBUG prints, and don't fix anything until you can point at the line.
  3. Fix that one line.
  4. Bonus: remove your DEBUG prints and leave the report clean.
The error sequence, run by run

Run 1 shows one error only:

run 1
Main.java:3: error: ';' expected
        String subsystem = "Arm"
                                ^
1 error

Run 2, after adding the semicolon, two errors appear that were hidden behind the first one:

run 2
Main.java:8: error: cannot find symbol
        double degrees = rotation * 360;
                         ^
  symbol:   variable rotation
  location: class Main
Main.java:10: error: incompatible types: possible lossy conversion from double to int
        int ticks = 4.0;
                    ^
2 errors

Run 3, after fixing rotation to rotations:

run 3
Main.java:10: error: incompatible types: possible lossy conversion from double to int
        int ticks = 4.0;
                    ^
1 error

Run 4, after int ticks = 4;, it compiles and prints rotations: 4.0. That's wrong: 90 ÷ 20 is 4.5.

The compiler could not even see errors 2 and 3 until error 1 was fixed. That's why you fix the top one and re-run.

solution · Main.java
public class Main {
    public static void main(String[] args) {
        String subsystem = "Arm";
        int encoderTicks = 90;
        int ticksPerRotation = 20;

        double rotations = (double) encoderTicks / ticksPerRotation;
        double degrees = rotations * 360;

        int ticks = 4;

        System.out.println(subsystem + " startup report");
        System.out.println("  rotations: " + rotations);
        System.out.println("  degrees:   " + degrees);
        System.out.println("  ticks:     " + ticks);
    }
}
output
Arm startup report
  rotations: 4.5
  degrees:   1620.0
  ticks:     4

Three errors cost you about ninety seconds, because each one named its own line. The fourth problem had no error message, so you had to go looking for it. That's the kind to worry about.
