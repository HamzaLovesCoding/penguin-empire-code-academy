Exceptions & the Null Trap

1 What null means

null means a variable holds no object. It is not zero and it is not an empty string. It is the absence of a thing.

Main.javaJava
String name = null;
System.out.println("name is " + name);       // name is null
System.out.println(name == null);            // true

You have already produced null without meaning to. An array of String starts every slot at null, and so does every cell of a String grid.

Main.javaJava
String[] subsystems = new String[2];
System.out.println(subsystems[0]);           // null

Only object types can be null. An int, double or boolean always holds a real value.

2 NullPointerException

Printing null is fine. Calling a method on it is not.

Main.javaJava
String name = null;
System.out.println(name.length());
console
Exception in thread "main" java.lang.NullPointerException:
        Cannot invoke "String.length()" because "name" is null

The message names the method you tried to call and the variable that was empty. That is usually enough to find the line without any other information.

There is nothing there to ask

A method call needs an object to act on. When the variable holds null there is no object, so Java stops rather than guessing. The fix is almost never to catch this. The fix is to work out why the variable was empty.

3 Checking before you use

Test for null with == or !=. This is one of the few places == is correct on an object.

Main.javaJava
String label = null;

if (label != null && label.length() > 0) {
    System.out.println("label ok");
} else {
    System.out.println("no label, skipping");
}
output
no label, skipping

The order matters. && stops as soon as the left side is false, so label.length() is never reached when label is null. Writing the two checks the other way round crashes.

4 Out of bounds

The other common crash comes from asking for a position that does not exist. You have seen all three forms.

String
StringIndexOutOfBoundsException from charAt or substring.
Array
ArrayIndexOutOfBoundsException from an index past the end.
ArrayList
IndexOutOfBoundsException from get.

All three messages tell you the index you asked for and the size you had. The cause is almost always a loop that ran one step too far.

5 try and catch

try marks code that might fail. catch says what to do if it does. Instead of stopping, the program runs the catch block and carries on.

Main.javaJava
int[] ids = {2, 3, 4};

try {
    System.out.println(ids[5]);
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("caught: " + e.getMessage());
}

System.out.println("program continues");
output
caught: Index 5 out of bounds for length 3
program continues

The variable e holds the exception. e.getMessage() gives the same text you would have seen in the crash. The last line proves the program survived.

The type in the parentheses decides what gets caught. Catching ArrayIndexOutOfBoundsException does not catch a NullPointerException.

6 finally

A finally block runs whether or not an exception happened.

Main.javaJava
try {
    System.out.println(10 / 0);
} catch (ArithmeticException e) {
    System.out.println("caught: " + e.getMessage());
} finally {
    System.out.println("finally always runs");
}
output
caught: / by zero
finally always runs

Use it for cleanup that must happen either way, such as stopping a motor.

7 Catch or fix

Catching an exception is not the same as fixing it. Most exceptions in your own code are bugs, and catching them hides the bug instead of removing it.

Fix the code when the exception means you made a mistake, such as a loop that runs past the end of an array.

Catch the exception when the failure is expected and the program has something sensible to do instead, such as a sensor that is not connected.

Never catch and do nothing

An empty catch block turns a loud crash into a silent wrong answer, which lesson 6 identified as the most expensive kind of bug. At minimum, print something.

10 Common mistakes

Watch out for these
  • Calling a method on a variable that might be null.
  • Putting the null check second, so the method call runs first and crashes.
  • Confusing null with 0 or with an empty string.
  • Catching an exception that is really a bug in your own loop.
  • Writing an empty catch block.
  • Catching the wrong type, so the exception you actually get is not caught at all.
Exercise

Survive the Bad Data

An array of subsystem names has a gap in it. Print a report without crashing.

  1. Loop over the array and print each name.
  2. Skip any slot that is null and print (empty slot) instead.
  3. Wrap a deliberate out of bounds read in try and catch, and print the caught message.
  4. Print a final line to prove the program survived.
Show one possible solution
solution · Main.java
public class Main {
    public static void main(String[] args) {
        String[] subsystems = new String[4];
        subsystems[0] = "Intake";
        subsystems[2] = "Shooter";

        for (int i = 0; i < subsystems.length; i++) {
            if (subsystems[i] == null) {
                System.out.println(i + ": (empty slot)");
            } else {
                System.out.println(i + ": " + subsystems[i]);
            }
        }

        try {
            System.out.println(subsystems[9]);
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("caught: " + e.getMessage());
        }

        System.out.println("report finished");
    }
}
output
0: Intake
1: (empty slot)
2: Shooter
3: (empty slot)
caught: Index 9 out of bounds for length 4
report finished

The null check is a fix, because those slots really are empty. The try and catch is a demonstration only. In real code that read would simply be removed.
