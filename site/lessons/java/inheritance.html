Inheritance (extends, super)

Inheritance lets one class take everything another class has and add to it. Every subsystem you write in Phase 2 inherits from a WPILib class, so this is the shape of real robot code.

1 The repetition problem

A robot has several subsystems. Every one of them has a name and a CAN ID, and every one can be stopped. Writing those three things into every class means changing every class when one of them changes.

Inheritance puts the shared parts in one class and lets the others take them.

2 extends

The shared class is called the parent or superclass. A class that takes from it is the child or subclass.

Main.javaJava
class Subsystem {
    protected String name;
    protected int canId;

    public Subsystem(String name, int canId) {
        this.name = name;
        this.canId = canId;
    }

    public String getName() { return name; }
    public void stop() { System.out.println(name + " stopped"); }
    public String report() { return name + " on CAN " + canId; }
}

class Intake extends Subsystem {
    public Intake(String name, int canId) {
        super(name, canId);
    }
}

Intake has name, canId, getName, stop and report without declaring any of them. It got all five from Subsystem.

3 super in the constructor

super(...) calls the parent's constructor. It must be the first line of the child constructor.

Main.javaJava
class Flywheel extends Subsystem {
    private double targetRPM;

    public Flywheel(String name, int canId, double targetRPM) {
        super(name, canId);           // must come first
        this.targetRPM = targetRPM;
    }

    public void spinUp() {
        System.out.println(name + " spinning to " + targetRPM);
    }
}

The parent sets up its own fields, then the child sets up the ones it added. Leaving out super(...) when the parent has no no-argument constructor gives constructor Subsystem in class Subsystem cannot be applied to given types.

4 Overriding a method

A child can replace a method it inherited by declaring one with the same name and parameters. Mark it @Override.

Main.javaJava
class Intake extends Subsystem {
    public Intake(String name, int canId) { super(name, canId); }

    @Override
    public void stop() {
        System.out.println(name + " rollers halted");
    }
}
output
Shooter stopped
Intake rollers halted

Calling stop() on a Flywheel runs the parent version. Calling it on an Intake runs the replacement.

@Override is worth writing

It is optional, but it makes the compiler check that you really are replacing something. Misspell the method name and you get an error instead of a method that silently never runs.

5 Calling the parent version

super.methodName() runs the parent's version from inside the override. Use it when the child adds to the parent's work rather than replacing it.

Main.javaJava
@Override
public String report() {
    return super.report() + ", target " + targetRPM + " RPM";
}
output
Shooter on CAN 5, target 4000.0 RPM

The parent produced the first half and the child appended to it. Without super.report() the child would have to repeat the name and CAN ID formatting.

6 protected

The last lesson used private to hide fields. A private field is hidden from child classes too, which is usually too strict for a base class.

private
This class only. Child classes cannot see it.
protected
This class and any class that extends it.
public
Anywhere.

Subsystem declares name as protected, which is why Intake can use it directly inside its own stop().

9 Common mistakes

Watch out for these
  • Forgetting super(...) when the parent has no no-argument constructor.
  • Putting super(...) after another statement.
  • Making base class fields private and then trying to use them in a child.
  • Misspelling an overridden method, which quietly creates a new method instead. @Override catches this.
  • Using inheritance when the two classes are not really related. Shared code alone is not a reason.
Exercise

A Subsystem Family

Build a base class and two children.

  1. Write Subsystem with protected name and CAN ID, a constructor, stop() and report().
  2. Write Arm extends Subsystem with a targetAngle field and a moveTo() method.
  3. Override report() in Arm so it calls super.report() and appends the angle.
  4. Write Climber extends Subsystem that overrides stop().
  5. Create one of each and call report() and stop() on both.
Show one possible solution
solution · Main.java
class Subsystem {
    protected String name;
    protected int canId;

    public Subsystem(String name, int canId) {
        this.name = name;
        this.canId = canId;
    }

    public void stop() { System.out.println(name + " stopped"); }
    public String report() { return name + " on CAN " + canId; }
}

class Arm extends Subsystem {
    private double targetAngle;

    public Arm(String name, int canId, double targetAngle) {
        super(name, canId);
        this.targetAngle = targetAngle;
    }

    public void moveTo() {
        System.out.println(name + " moving to " + targetAngle + " degrees");
    }

    @Override
    public String report() {
        return super.report() + ", target " + targetAngle + " degrees";
    }
}

class Climber extends Subsystem {
    public Climber(String name, int canId) { super(name, canId); }

    @Override
    public void stop() {
        System.out.println(name + " locked in place");
    }
}

public class Main {
    public static void main(String[] args) {
        Arm arm = new Arm("Arm", 3, 45);
        Climber climber = new Climber("Climber", 7);

        System.out.println(arm.report());
        arm.moveTo();
        arm.stop();

        System.out.println(climber.report());
        climber.stop();
    }
}
output
Arm on CAN 3, target 45.0 degrees
Arm moving to 45.0 degrees
Arm stopped
Climber on CAN 7
Climber locked in place

Arm did not override stop(), so it used the inherited version. Climber did not override report(), so it used the inherited one. Each class only writes the parts that differ.
