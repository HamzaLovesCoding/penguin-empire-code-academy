1 Why this matters

Eight Krakens or a harder afternoon

The CTRE Swerve Generator is, by our curriculum's account, fast and easy. You feed it your robot's dimensions and centre of mass and it writes the swerve code for you to import.

There is one condition. It requires eight Kraken and CTRE motors. Not works best with. Requires.

So this is not really a software decision. It was made months earlier, when somebody ordered motors. If your drivetrain is all CTRE, take the easy path. If it is mixed, or REV, you need YAGSL, which works across brands and is harder to set up.

That is the honest shape of a lot of FRC engineering. The best tool is the one your hardware allows, and your hardware was chosen before you got here.

2 Why generate at all

Recall what the previous lesson described. Four modules, each needing an angle and a speed derived from three driver inputs and the gyro heading. Wheel angles optimised so a module turns 90 degrees rather than 270. Odometry, so the robot tracks where it is. Per-module closed-loop control on both motors.

That is a large amount of trigonometry which has to be exactly right, and every team in FRC needs the same trigonometry. Our curriculum's own note is that students rarely write swerve from scratch.

YAGSL stands for Yet Another Generic Swerve Library, and the name tells you its priority. It is generic. It does not care what motors you bought, and you pay for that flexibility in setup time.

Verify for current season, and take this one seriously

This is one of the two most volatile lessons in the whole track. Tool names, which application hosts the generator, configuration file formats, version numbers and licensing all change between seasons.

Read both vendors' current documentation before you start, and check whether CTRE's swerve features need a licence or activation for your season. The decision criterion on this page, which is that hardware decides the tool, and the list of measurements in section 4 are stable. Nothing else here is.

There is deliberately no Java on this page

Neither of this course's sources verifies a swerve API, and the drive-request calls differ between the two tools and between versions of each. Printing an invented method signature here would teach you a call that does not exist.

The reference you should actually read is your own team's generated drive subsystem, in your own project, for your own season. Open it. It is a subsystem like any other, and after Unit 7 you can read one.

4 What the generator needs from you

This is the most transferable part of the lesson, because it is true of both tools and of PathPlanner in Unit 11.

ValueWhy it is needed
Track width and wheelbaseThe kinematics is entirely about where the wheels sit relative to the centre
Mass and moment of inertiaHow heavy it is and how hard it is to spin
Centre of massWhere the weight actually sits, which is rarely the geometric middle
Gear ratios and wheel diameterTo convert motor rotations into metres travelled
CAN IDs for eight motors and four encodersSo the code addresses the right device
Steering encoder offsetsSo each module knows which reading means straight forward

That fourth row is the conversion factor problem from Unit 5, at drivetrain scale. The encoder counts motor rotations, and the code needs metres.

Measurements are inputs to correctness

A generator fed the wrong wheelbase produces code that compiles, deploys, runs and drives slightly wrong forever. There is no error message for a mistyped dimension, and there never will be, because the software has no way to know what your robot is shaped like.

Get a tape measure. Measure wheel centre to wheel centre, not edge to edge. Have a second person check the number before it goes into the tool.

5 Encoder offsets, the step that always bites

Each steering module's absolute encoder reads some angle when the wheel points straight forward, and it is never zero. It depends on how the encoder happened to be bolted on.

So setup involves physically aligning all four wheels forward and recording what each encoder reads at that moment. Those four numbers become the module offsets.

offsets correct one offset wrong / / / / / / / / three modules agree robot robot / / / \ one module points / / / \ somewhere else all four agree. the odd wheel drags sideways. robot drives straight. robot crabs, and that module is audibly fighting the others.
Learn the symptom, not just the procedure

One wheel fighting three is the signature of a wrong encoder offset. The robot drives crabwise instead of straight, and one module makes a noise the others do not.

Compare that with the gyro bug from the last lesson, where all motion is rotated consistently and nothing fights anything. Two different symptoms, two different causes, and telling them apart in the pits saves you an hour.

Offsets are also not a one-time thing. Re-check them after any mechanical work on a module. A module that has been apart is a module whose offset you no longer know.

6 What generated code means for you

  • You will have a drive subsystem you did not write. That is fine and it is normal.
  • You will still write the commands that use it, exactly like every other subsystem.
  • Do not hand-edit generated files. Change the configuration and regenerate, or your edits disappear the next time anybody regenerates, which will happen at the worst possible moment.
  • It is still a subsystem. It registers with the scheduler, it has a periodic(), and commands require it. Everything from Unit 7 applies to it unchanged.

That last point is why Unit 9 comes after Unit 7. A student who understands subsystems can open a generated drive subsystem and read it. A student who does not has an opaque black box that either works or does not.

What you will call on it is, in plain terms, a request to translate at this speed in this direction while rotating at this rate, field-centric. That is three numbers, and they come from the two sticks. Your teleop binding reads the sticks, applies the deadband from the controllers lesson, and passes them in. The exact method name is a question for your season's documentation.

8 Common mistakes

Watch out for these
  • Thinking a generator means you do not understand swerve. You need field-centric behaviour, module geometry and encoder offsets to configure one at all. What you skip is retyping solved trigonometry.
  • Trying to use the CTRE generator with REV motors. It requires CTRE hardware throughout. That is what YAGSL is for.
  • Expecting the generator to work out the robot's dimensions. You measure them and type them in, and a wrong number produces code that drives wrong forever with no error.
  • Hand-editing a generated file. Regenerate instead. Hand edits disappear the next time anyone regenerates.
  • Treating a generated drivetrain as not a real subsystem. It is one. Everything from Unit 7 applies.
  • Treating encoder offsets as a one-time setup. Re-check after any mechanical work on a module.
Build it · PenguinBot

The drivetrain decision document

PenguinBot's CAN map reserves IDs 10 to 17 for eight swerve motors and nothing has been generated yet. Write the document a team would actually produce before starting.

  1. State the hardware and the generator that follows from it, with a one sentence justification.
  2. List every measurement and value you need to collect before running the generator, and who on the team you would get each one from.
  3. Write the encoder offset procedure as numbered steps somebody else could follow without asking you anything.
  4. Write the first-drive test plan: what you check, in what order, at what speed.
  5. State what would change in your answer if half the drivetrain were REV.
Reveal the solution

1. PenguinBot runs eight Krakens, drive on 10 to 13 and steer on 14 to 17. All CTRE, so the CTRE Swerve Generator. It is the fast path and our hardware meets its requirement exactly.

3. Encoder offset procedure

  1. Put the robot on blocks so the wheels turn freely.
  2. Rotate all four wheels by hand until they point straight forward and are parallel. Use a straight edge across each pair. Eyeballing it is not good enough.
  3. In the vendor client, read and write down each steering encoder's current reading.
  4. Enter those four readings as the module offsets in the generator's configuration.
  5. Regenerate, deploy, and re-check. Commanded to zero, all four wheels should return to straight forward.

4. First-drive test plan, on blocks first and then on the floor, slowly.

  1. On blocks, enabled, no stick input. Nothing should move. If a module creeps, its offset or its closed loop is wrong.
  2. On blocks, stick forward. All four wheels should point forward and spin the same way.
  3. On blocks, right stick only. Wheels should splay tangentially and spin to rotate the robot.
  4. On the floor, low speed, robot facing the driver. Push forward. It should move away in a straight line.
  5. Rotate the robot 90 degrees by hand, re-zero nothing, push forward again. Field-centric means it should still travel in the same direction across the field. If it does not, the gyro or the field-centric flag is wrong.
  6. Only then, raise the speed.

Step 5 is the one people skip, and it is the only step that actually tests field-centric control.

5. If half were REV, the CTRE generator is unavailable, because it requires CTRE hardware throughout. It would be YAGSL, and we would budget significantly more setup time. The physical measurements and the encoder offset procedure are identical either way, because those are facts about the robot rather than about the software.
