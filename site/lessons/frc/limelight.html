1 Why this matters

Re-tune it for every venue

The camera is configured through a web page: brightness, exposure, and how it decides what counts as a target. Our curriculum's instruction is unambiguous. Re-tune before every competition, for that venue's lighting.

Think about what that implies. A gym with skylights at ten in the morning is a different optical environment from the same gym under floodlights at eight at night, and both are different from your workshop. Your vision code does not change. Your robot does not change. But a camera tuned for a dim workshop can be effectively blind in a bright arena, and the failure looks exactly like broken code.

Put it on the game-day checklist. It is one of the very few programming tasks that has to be done at the venue, and it takes fifteen minutes you will not have if you did not plan for it.

2 What an AprilTag is

A flat, printed, square marker with a number encoded in its pattern. The field has them mounted in published positions, so a robot that recognises one knows something about where it is.

an AprilTag +-------------------+ | ### ## ###### | a pattern that encodes ONE number | # ## ### # ## | | #### # ##### | the robot reads: "this is tag 7, | # ### #### # | and I am looking at it from 12 | ## # ## ### | degrees off to the left" +-------------------+ it carries an ID. not a URL, not a message.

Spelling matters here because you will search for it. It is AprilTag, one word, capital A and capital T. Our curriculum writes it as two words and that is worth correcting, because searching for the wrong spelling costs you time.

Verify for current season

How many tags the field carries, where they are, and which ID means what are all game-specific and change every year. This lesson deliberately states no tag count and no ID meanings. Get them from the current season's field drawings, and treat any tag ID you find in old code as wrong until you check.

3 What the camera actually sends

A Limelight is a camera with a processor inside it. It is used widely across FRC.

The important thing about it is what it does not do. It does not hand your robot images. It does the vision work on the camera and publishes numbers.

That matters for a reason you can now appreciate. Your roboRIO has 20 milliseconds per loop to run every subsystem's periodic(), poll the buttons and execute every scheduled command. It has no budget to process video. Because the camera does that work, your code receives a handful of doubles and your loop stays fast.

Both TX and TY are angles. Neither is a distance. TY correlates with distance, which is what makes it useful for range control, but nothing here measures metres.

5 TX is already an error

This is why Unit 6 came first

In Unit 6 you built controllers around error = setpoint - current. You needed an encoder to measure the current value, and you did the subtraction yourself.

Here the setpoint is zero, meaning facing the tag, and the camera hands you the error directly. No encoder. No subtraction. No conversion factor.

TX is the number you feed to a PID controller. That is what this unit was building toward, and the next lesson writes the twelve lines that do it.

6 The reading that is not there

Here is the most important practical point on this page, and neither of this course's sources states it, so reason it out.

What does TX read when no tag is visible?

tag centred tag out of frame [tag] (nothing in view) | | TX = 0.0 TX = 0.0 | [robot] [robot] "perfectly aimed" "no idea where anything is" ONE NUMBER. TWO COMPLETELY DIFFERENT SITUATIONS.
A robot that trusts TX blindly stops the moment it loses the tag

Your aiming code drives TX toward zero. The tag leaves the frame. TX becomes zero. Your code concludes it is perfectly aimed and stops turning, pointing at nothing in particular.

So every vision subsystem needs a has target check, and every vision command must ask it before acting on any reading. The next lesson builds exactly that guard, and this is why.

7 Wrap it in your own subsystem

Our curriculum's stated best practice: the Limelight provides a helper file, which is a collection of static methods, rather than a class you create an instance of. Do not scatter calls to it through your codebase. Write a LimelightSubsystem that exposes readable methods.

Three concrete reasons, and the second is the one that matters most in February.

  • Your commands read limelight.getAngleToTag() rather than a static call with a string argument, and one of those says what it means.
  • When the vendor's API changes between seasons, one file changes instead of every command.
  • The has-target guard lives in one place, so nothing can forget it.
Why the vendor calls below are commented out

Neither of this course's sources gives verified signatures for the Limelight helper methods, and those signatures have changed between versions. Printing a guess would teach you a call that does not exist, so the wrapper below shows the shape with the vendor calls as comments.

Fill them in from the current Limelight documentation for your season. The configuration address, pipeline switching and the exact has-target reading all need checking there too. The structure on this page is what is stable.

subsystems/LimelightSubsystem.javaJava
import edu.wpi.first.wpilibj2.command.SubsystemBase;

public class LimelightSubsystem extends SubsystemBase {

    // Readable names for the rest of the robot. The vendor calls live HERE
    // and nowhere else, so a season's API change touches one file.

    public double getAngleToTag() {
        // return LimelightHelpers.getTX(...);      <-- fill in from vendor docs
        return 0.0;
    }

    public double getVerticalAngleToTag() {
        // return LimelightHelpers.getTY(...);
        return 0.0;
    }

    public int getTagId() {
        // return (int) LimelightHelpers.getFiducialID(...);
        return -1;
    }

    public boolean hasTarget() {
        // Critical: TX reads 0 with no target, which looks exactly like "aimed".
        // Nothing may trust a reading without checking this first.
        return false;
    }
}

The method names are the deliverable here. getAngleToTag() says what it means and getTX() does not, and a teammate reading your command six weeks from now will thank you.

There is no sandbox on this page

There is no camera, and faking image processing would teach you nothing true. The next lesson puts a clearly documented stand-in Limelight in a sandbox so the control loop can be real code you run, which is the part that actually transfers.

One more piece of vocabulary. A pipeline is a saved camera configuration you can switch between, so a team might have one tuned for AprilTags and another for something else entirely, and select between them from code.

9 Common mistakes

Watch out for these
  • Thinking the camera sends video to the robot. It processes on-camera and publishes numbers, which is why your loop stays fast.
  • Reading TX as a distance. TX and TY are both angles. TY changes with distance, which is how you use it for range, but neither is a measured distance.
  • Believing TX equals zero means centred. Or that there is no target at all. Check has-target before you believe it.
  • Calling AprilTags QR codes. Similar idea, different system. A tag carries an ID, and the field's tag positions are published so the robot can locate itself.
  • Treating the camera as configured once. Re-tune for every venue's lighting.
  • Calling the vendor helper directly from your commands. Then next season's API change touches every command instead of one subsystem.
Build it · PenguinBot

PenguinBot gets eyes

PenguinBot can score from one button and drive field-centrically. It has no idea where the goal is.

  1. Write LimelightSubsystem extends SubsystemBase with the four readable methods from section 7.
  2. Add isTargetValid(), true only if there is a target and its ID is one PenguinBot should act on. Put the acceptable IDs in a VisionConstants block.
  3. Add a periodic() that publishes all four values so you can see them while debugging.
  4. Leave the vendor calls commented, with a note saying where the real signatures come from.
  5. Write the two lines you would add to the game-day checklist about this camera.
Reveal the solution
Constants.java · new blockJava
public static final class VisionConstants {
    public static final String kLimelightName   = "limelight";
    public static final double kAimToleranceDeg = 1.0;       // used next lesson

    // VERIFY AGAINST THIS SEASON'S FIELD DRAWINGS. Tag layouts change
    // every year, and last year's IDs will compile perfectly.
    public static final int[] kScoringTagIds = { 7, 8 };
}
subsystems/LimelightSubsystem.javaJava
import edu.wpi.first.wpilibj2.command.SubsystemBase;
import static frc.robot.Constants.VisionConstants;

public class LimelightSubsystem extends SubsystemBase {

    // The vendor calls live ONLY in this file. When the API changes between
    // seasons this is the only file that changes. Fill these in from the
    // current Limelight documentation.

    public double getAngleToTag() {
        // return LimelightHelpers.getTX(VisionConstants.kLimelightName);
        return 0.0;
    }

    public double getVerticalAngleToTag() {
        // return LimelightHelpers.getTY(VisionConstants.kLimelightName);
        return 0.0;
    }

    public int getTagId() {
        // return (int) LimelightHelpers.getFiducialID(VisionConstants.kLimelightName);
        return -1;
    }

    public boolean hasTarget() {
        // TX reads 0 with no target, which is identical to "perfectly aimed".
        // Nothing may trust a reading without checking this first.
        return false;
    }

    // The guard every vision command should actually call.
    public boolean isTargetValid() {
        if (!hasTarget()) return false;
        int id = getTagId();
        for (int allowed : VisionConstants.kScoringTagIds) {
            if (id == allowed) return true;
        }
        return false;      // a real tag, just not one of ours
    }

    @Override
    public void periodic() {
        // Publish for debugging. Vision problems are invisible without this.
        System.out.printf("limelight: tx %.2f  ty %.2f  id %d  target %b%n",
                          getAngleToTag(), getVerticalAngleToTag(),
                          getTagId(), hasTarget());
    }
}

Game-day checklist lines

  1. Re-tune the Limelight for this venue's lighting before the first match, brightness and exposure, at the field if we can get access to it.
  2. Confirm the tag IDs in VisionConstants match this game's field layout, and watch the published ID on the dashboard during a practice match to be sure we are seeing the tags we think we are.

Two things in that solution matter more than the syntax.

  • isTargetValid() combines "is there a target" with "is it one of ours" into the single method every command should call. Aiming at the other alliance's tag is a real failure and an embarrassing one.
  • The VERIFY comment on the tag IDs is doing real work. Tag layouts are game-specific, and last season's IDs will compile perfectly while aiming at nothing.
