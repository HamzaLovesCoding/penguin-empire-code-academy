1 Why this matters

The most senior skill on this page is not writing code. It is knowing when code is not ready to ship.

The voice controlled ChairBot

A team member built voice control for the team's ChairBot. It ran a small offline speech model, so it needed no internet and no paid service, and it sent recognized commands to the robot over the network. It worked.

It may never go on the real robot. One drive motor pulled to the right and needed constant correction, and the only safety feature was having to hold something down while giving a command. A prototype that works most of the time, on a machine that weighs more than you do, is a hazard.

The team raised those safety concerns before it went anywhere near the real robot. That caution, not the speech model, is the thing worth copying.

A second thing to expect early: your tools will fail you. One season the team tried to run robot code in simulation so software could make progress before the robot existed. They never got it stable and went back to waiting for real hardware. Working around broken tooling is a normal part of this job, not a sign you are doing it wrong.

2 You are not the person who types

The mechanical sub-team builds an arm out of aluminum. That arm has no idea where it is, when to stop, or how hard to push. Your work is what turns a moving assembly into a mechanism that can be aimed, repeated, and trusted.

Concretely, across a season you will:

  • Make each mechanism move on command.
  • Read sensors so the robot knows the position and speed of every mechanism.
  • Hold a mechanism at a target instead of slamming past it.
  • Bind behaviors to controller buttons so a driver can use them.
  • Make the robot see where it is on the field.
  • Chain all of it into a routine that runs with nobody driving.

Those six bullets are Units 4 through 11 of this phase, in order.

3 Three workstreams, in order

Software work on an FRC robot splits into three streams. They have a strict dependency order, and the order is the most useful thing on this page.

MECHANICS → VISION → AUTONOMOUS (Units 4-8) (Units 9-10) (Unit 11) make it know where do it with move you are nobody driving

Mechanics is making an intake spin and an arm lift to a position. Vision is making the robot report how far off target it is. Autonomous is the opening seconds of a match, when no human is driving.

Autonomous comes last because of what it is made of. An autonomous routine is a list of the commands you already wrote for your mechanisms, pointed at the field by your vision readings. If the arm command does not exist yet, there is nothing to put in the list. This is why Unit 11 is the last unit in this course.

Verify for current season

The autonomous period is short, on the order of the first fifteen to twenty seconds of a match, but its exact length and what it scores change with every year's game. Read this season's game manual for the real numbers.

4 Programmers touch hardware

This surprises most new members. Software owns several physical jobs that nobody else on the team does:

  • Imaging the roboRIO. The robot's controller has to be flashed with the current season's image before it will accept your code.
  • Configuring the radio. The robot's radio has to be set up with your team number before a laptop can reach the robot.
  • Pushing motor controller firmware. Out of date firmware on a motor controller produces failures that look exactly like code bugs.
  • Assigning CAN IDs. Every motor controller needs a unique number, set over USB with a vendor tool, before your code can address it.

You cannot debug a signal path you cannot picture. That is the reason Unit 1 is wiring and Unit 2 is tools, and neither of them asks you to write a line of Java.

5 Write, deploy, watch, adjust

In Phase 1 you wrote code, ran it, and read the output. Robot code has the same loop with a longer middle step:

WRITE → DEPLOY → WATCH → ADJUST edit push to enable and change one code the RIO look at the number and real robot go again

Nothing about a mechanism is verified by reading the code. Here is the standard example, and you will meet it for real in Unit 4: when you tell a motor to run at positive speed, you do not know which physical direction that is until you run it slowly and watch. Not because the documentation is bad, but because it depends on how the motor was mounted and how the gearbox was assembled.

The one rule for the next 29 lessons

Say out loud when something does not make sense, and keep poking at it until it does. Nodding along costs the team more than asking does. This applies to your teammates, to this website, and to the official documentation.

6 The shape of a season

Three phases repeat every year.

Build season
Weeks of nightly iteration. Mechanisms appear one at a time and you program each one as it becomes real. Most of your code is written here.
Competition
You go to the field with the drive team, bring the driver station laptop, and watch the console for errors during matches. Unit 12 covers this day in detail.
Offseason
Learning and side projects, like the ChairBot voice control experiment. This website is one too.

Put them in orderWhat has to happen first?

Your team wants a robot that drives itself to the goal and scores during autonomous. Drag these four jobs into the order you have to do them, first at the top.

  • Write the auto routine
  • Make the arm lift to a setpoint
  • Make the Limelight report the angle to the tag
  • Make the intake motor spin
Hint

Ask what each job needs in order to exist. The auto routine needs commands to sequence. Aiming needs something that can move. Start from the simplest single motor.

8 Common mistakes

Ideas new members arrive with
  • "Programming is the last step. Mechanical builds it, then we code it." Software runs alongside the build. You will be assigning CAN IDs and spinning motors on a half built robot, which is why Units 1 and 2 are hardware and tools.
  • "Autonomous is the impressive part, so we should start there." Autonomous is the easy part once everything else works, because it is a list of commands you already wrote. Before then it is impossible, not hard.
  • "If I break something, I have failed." Every season this team has broken something, including a fried motor and a mechanism that fell off from bad tuning. What separates a good programmer is starting low, raising slowly, and saying out loud when something does not make sense.
  • "I need a powerful laptop for this." One captain's computer died mid season and he wrote code on the driver station laptop for the rest of the year. You will meet that story properly in Unit 2.
Plan it · PenguinBot

Map your season

Every exercise in this phase adds one capability to the same robot. Meet it now.

PenguinBot

PenguinBot is a teaching robot: a roller intake, a pivoting arm that lifts a game piece to a scoring setpoint, a swerve drivetrain, and a Limelight that finds the scoring tag.

  1. Write the order. In your own words, list the order you would work in to make PenguinBot score a game piece by itself.
  2. Then answer this. In one sentence: what breaks if you build the vision code before the arm works?
Reveal a reference answer
  1. Spin the intake motor (Unit 4).
  2. Read the arm's encoder so the code knows where the arm is (Unit 5).
  3. Use PID so the arm stops at the scoring position instead of slamming past it (Unit 6).
  4. Turn that into a Command with a clear end, owned by a Subsystem that holds the motors (Unit 7).
  5. Bind it to a controller button, then chain arm up, outtake, arm down (Unit 8).
  6. Make the robot drive (Unit 9).
  7. Use the Limelight's horizontal angle reading to aim (Unit 10).
  8. Only now: draw a path and sequence those commands into an auto routine (Unit 11).

If you build vision first you get a robot that can tell you it is 12 degrees off target and can do nothing about it. Vision only produces an error number. Something else has to act on it.

That list is this entire phase. By Unit 11 you will have written every step of it.
