1 Why this matters

Count what you are about to write

PenguinBot's autonomous needs an arm that reaches a setpoint, an intake that runs, a scoring sequence, a drivetrain, and a command that aims at a tag.

Every single one of those already exists. You built them in Units 4 through 10.

The genuinely new code in this lesson is a list, a chooser and a timeout, and nothing else. Autonomous feels impossible when you attempt it first and nearly trivial when you attempt it last, and the difference is entirely ordering.

Autonomous is the most fragile code on the robot

Nobody can intervene. There is no driver to press another button, no way to nudge it, no chance to try again.

And an autonomous period of a robot doing nothing looks identical, from the stands, to a robot that was never programmed at all. That is what the timeout section of this lesson is for.

2 A routine is a sequential group

You already know how to write one. Autonomous is the same composition you did in Unit 8, with paths mixed in.

AutoRoutine (sequential) | +-- Path: start line -> in front of the goal (approximate) +-- AimAtTagCommand (precise) +-- ScoreSequence (already built and tested) +-- WaitCommand (let it settle) +-- Path: goal -> out of the way

Every box except the two paths is a command that is already running in teleop, unchanged.

commands/ScoreAndLeaveAuto.javaJava
import edu.wpi.first.wpilibj2.command.SequentialCommandGroup;
import edu.wpi.first.wpilibj2.command.ParallelCommandGroup;
import edu.wpi.first.wpilibj2.command.WaitCommand;

public class ScoreAndLeaveAuto extends SequentialCommandGroup {

    public ScoreAndLeaveAuto(DriveSubsystem drive, LimelightSubsystem limelight,
                             ArmSubsystem arm, IntakeSubsystem intake) {
        addCommands(
            // Drive to the goal WHILE raising the arm. Different subsystems.
            new ParallelCommandGroup(
                // PathPlanner path here: start line to the scoring position
                new ArmToScoreCommand(arm)
            ),

            new AimAtTagCommand(drive, limelight),   // precise, closes the last few degrees
            new ScoreSequence(arm, intake),          // already built, already tested
            new WaitCommand(0.25),                   // settle before moving off

            // PathPlanner path here: scoring position to out of the way
            new ArmToStowCommand(arm)
        );
    }
}

The paths are comments because PathPlanner's API is not verified in this course, as the previous lesson explained. Everything else in that file is a class you wrote.

RobotContainer.javaJava
public Command getAutonomousCommand() {
    return new ScoreAndLeaveAuto(drive, limelight, arm, intake);
    // With a chooser: return autoChooser.getSelected();
}

That is the stub from Unit 8, finally returning something. autonomousInit() calls this method and schedules the result, and that plumbing has been sitting there unused since Unit 8. Nothing about Robot.java changes.

3 Parallel matters more here

Autonomous is time-limited, so time saved is points scored. The arm can be raising while the robot drives to the goal, because they are different subsystems and there is no conflict.

In Unit 8 the same idea saved you a single scheduler cycle and the point was the pattern. Here it is worth real time, and the sandbox below measures exactly how much.

The constraint from Unit 8 still applies without exception: two commands needing the same subsystem cannot be in the same parallel group.

4 The chooser

A dropdown on the dashboard lets the drive team pick which routine runs before the match: a two-piece auto, a simple drive-off-the-line auto, or do nothing.

That last option earns its place. Alliance strategy changes match to match, and doing nothing is sometimes the correct choice when the alternative is colliding with a partner who is running their own routine through the same space.

The chooser lives in RobotContainer and is read by getAutonomousCommand(), which is wiring you have already seen.

Verify for current season

The chooser class and how it is published to the dashboard are WPILib details that have moved between versions, and there is no verified sample for them in this course's sources. Check the current documentation. The idea, which is that the drive team picks a routine and getAutonomousCommand() returns whichever they picked, is stable.

5 Timeouts are not optional here

In teleop, a stuck command means the driver presses another button. In autonomous nobody can intervene, so a command that never finishes means the rest of the routine never runs. Silently, for the whole period.

Three things can hang, and you have already met all three.

  • ArmToScoreCommand if the arm jams. Unit 7 gave it a timeout, and this is why.
  • AimAtTagCommand if the tag is never seen, or if the robot hunts around the tolerance without ever satisfying it. Unit 10's second bonus.
  • A path, if the robot is physically blocked by another robot.
The most valuable sentence in Unit 11

Every command in an autonomous routine needs a way to end that does not depend on succeeding.

A timeout, a maximum tick count, a give-up condition. Something. A command whose only exit is success will, on the day it does not succeed, hold the entire routine for the rest of the period while the scoreboard stays at zero.

6 Design to degrade gracefully

A routine that scores two pieces when everything works and zero when anything does not is worse than one that scores one piece reliably.

So order the routine with the most valuable and most reliable action first, and the ambitious part last. Then a failure late in the routine costs you the bonus rather than the baseline.

That is a strategy decision rather than a programming one, and it is the kind of thing a programmer is uniquely placed to notice, because you are the only person who knows which step is most likely to fail.

7 Run a whole autonomous period

Paths are a visible stand-in

PenguinSim has no drivetrain and no field, so a path is represented by a FakePathCommand defined in the file you are reading. It takes a fixed number of ticks and then finishes.

That is an honest stand-in, because what matters for sequencing is exactly that: a path takes time and then it ends. The group classes are hand-rolled here too, for the same reason as in Unit 8.

Read the first block. The path finished at 40 ticks while the arm was still climbing, and the parallel group waited for the slower member before moving on. Nothing coordinated that. They are different subsystems, so they simply ran at the same time.

Experiment 1 · measure what parallel is worth

Change both Parallel blocks to Sequence and run it again.

StructureRoutine finished at
Paralleltick 176
Sequentialtick 241

Sixty five ticks, which is 1.3 seconds of a period that is only worth a few seconds in the first place. That is not a rounding error. In a real routine that is the difference between fitting a second scoring cycle in and not.

Experiment 2 · the silent hang

Set the to-goal path to 300 ticks, which is longer than the whole simulated period.

output · tail
tick 150   arm 49.73   roller  0.00
tick 175   arm 49.73   roller  0.00
tick 200   arm 49.73   roller  0.00
tick 225   arm 49.73   roller  0.00
tick 250   arm 49.73   roller  0.00
=== AUTONOMOUS END ===
Look at what is missing from that output

No outtake. No score. No ROUTINE FINISHED. The arm reached its setpoint at 49.73 and then sat there for two hundred ticks while the first parallel block waited for a path that was never going to finish.

No error. No warning. From the stands, a robot that raised its arm and stopped.

Now notice what did work. The arm's own timeout meant the arm command ended cleanly rather than adding a second hang on top of the first. That is the Unit 7 timeout doing its job, and it is the difference between one broken step and a broken routine.

Experiment 3 · reorder for graceful degradation

Move ScoreSequence before the first path. Now if the path hangs, you have already scored. Then think about which ordering is correct for your actual routine, because the answer depends on whether the robot has to move before it can score.

8 Testing

  • Run it ten times, not twice. Two successful runs tell you almost nothing about a routine with this many moving parts.
  • Vary the battery. A flat battery accelerates differently, and paths are computed from physics.
  • Vary the starting position slightly. Does vision recover it, or does the whole routine drift?
  • Block the tag on one run. Does the routine hang, or does it degrade?
  • Watch the console every run. The next unit is about doing exactly this at a competition.

10 Common mistakes

Watch out for these
  • Writing new commands for autonomous. If you are writing many, something earlier in the season went wrong. Auto reuses teleop commands.
  • Shipping a step with no timeout. In teleop the driver rescues you. In autonomous nobody does.
  • Building the ambitious routine first. Score the reliable thing, then attempt the bonus.
  • Using parallel for commands that share a subsystem. The constraint from Unit 8 does not relax because autonomous is short on time.
  • Trusting two successful runs. Run it ten times, varying the battery and the starting position.
  • Not watching the console. A routine that silently did nothing looks the same as one that was never written.

You designed this routine last lesson. Build it.

  2. Put the drive and the arm raise in a parallel block, and say in a comment why that is safe.

Reveal the solution

The routine is the one in section 2. What matters is the audit.

3. How every command can end without succeeding

CommandHow it ends without succeeding
ArmToScoreCommandTick timeout from Unit 7. Already present
AimAtTagCommandFinishes when the target goes invalid, plus a tick timeout from Unit 10. Both present
ScoreSequenceEvery member is instant or a wait, except the arm commands, which are covered above
WaitCommandAlways ends. Time is the one thing that never gets stuck
Each pathNeeds checking. If PathPlanner's path command has no timeout, wrap it in one
ArmToStowCommandSame timeout as the score command

Notice that the audit found exactly one gap, and it was in the only part of the routine you did not write. That is normal, and it is why the audit is a step rather than an assumption.

4. What changed in Robot.java: nothing. autonomousInit() already asks RobotContainer for a command and schedules whatever it gets, and teleopInit() already cancels it. That plumbing has been sitting there since Unit 8 waiting for this moment.

Bonus 1. Three entries in the chooser: the full score-and-leave routine, a drive-off-the-line routine that is one path and nothing else, and do nothing. The drive team picks from the dashboard dropdown during the pre-match, based on what their alliance partners are doing. Write the options down on the pit whiteboard so the choice is a decision rather than a guess made under pressure.

Bonus 2. Move ScoreSequence before AimAtTagCommand, so the piece goes out whether or not the camera cooperated.

What you gave up: accuracy. Scoring without aiming means scoring from wherever the path happened to put you, which may well miss. So this reordering is only correct if a missed shot is worth more than no shot, which depends on the game. That is a strategy conversation to have with your drive team rather than a decision to make alone at a keyboard.
