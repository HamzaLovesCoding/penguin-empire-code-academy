1 Why this matters

The flywheel, finally

Unit 3 used a flywheel to explain why some behaviours need an end, and promised you would watch one run. Here it is.

A flywheel is heavy and hard to start, and once it is moving it holds its speed. You cannot shoot until it reaches 4000 RPM. Slam it to full power to get there quickly and you cook the motor, which Unit 4 covered at length. Ease it up and you have to know when it is ready.

You have every piece already. An encoder that reports velocity, from Unit 5. A safe output limit, from Unit 4. The idea of a behaviour with an end, from Unit 3. What has been missing is the thing that calls your code every 20 milliseconds and asks, over and over, whether you are done yet.

That thing is the CommandScheduler. In the sandbox below you will watch it work, tick by tick, and see exactly how many cycles the flywheel needs.

2 The four methods

Verified names · use the right-hand column

You will hear these called by informal nicknames. The real method names are what you type.

Often calledReal methodRuns
startinitialize()Once, when the command begins
periodicexecute()Repeatedly, every 20 ms while active
endend(boolean interrupted)Once, when the command stops
isFinishedisFinished()Every cycle, and returning true ends the command

Here is the skeleton. Every command you write for the rest of your FRC career looks like this.

SpinUpFlywheel.javaJava
import edu.wpi.first.wpilibj2.command.Command;

public class SpinUpFlywheel extends Command {

    private final Flywheel flywheel;
    private static final double TARGET_RPM = 4000.0;

    // The command is HANDED the mechanism. It never builds hardware itself.
    public SpinUpFlywheel(Flywheel flywheel) {
        this.flywheel = flywheel;
    }

    @Override
    public void initialize() {
        // once, at the start
    }

    @Override
    public void execute() {
        flywheel.setSpeed(0.8);                        // every 20 ms while scheduled
    }

    @Override
    public boolean isFinished() {
        return flywheel.getVelocity() >= TARGET_RPM;   // checked every cycle
    }

    @Override
    public void end(boolean interrupted) {
        flywheel.stop();                               // once, whatever stopped it
    }
}

Three things worth naming in that class.

  • The constructor takes the mechanism. A command reaches hardware by being handed it, never by creating a motor itself. If every command built its own SparkMax(5, ...) you would have several objects fighting over one motor.
  • The 0.8 is the 80 percent rule, not a coincidence.
  • isFinished reads a sensor. This is why Unit 5 had to come first. Without a velocity reading there is no end condition, only a guess.
Verify for current season

The base class name has changed before. Current WPILib uses extends Command, and older projects say extends CommandBase. If you open a repository from a previous season and see the older name, that is why. The four method names have been stable throughout.

Modern WPILib also offers shorter ways to build simple commands through factory methods. They are worth learning later. Writing the class by hand once is what makes the lifecycle visible, so do that first.

execute() and periodic() are not the same method

These get confused more than any other pair in the framework, so learn the difference now.

  • execute() belongs to a Command and runs only while that command is scheduled.
  • periodic() belongs to a Subsystem and runs always, scheduled or not.

Both are on the same 20 millisecond loop. Different owners, different lifetimes. The next lesson prints them side by side.

3 isFinished decides when it ends

Return true and the command ends immediately. Return false and it never ends on its own. Both are legitimate.

two valid end conditionsJava
// Ends when the arm arrives.
@Override
public boolean isFinished() {
    return arm.atSetpoint();
}

// Never ends on its own. Correct for "run while the button is held".
@Override
public boolean isFinished() {
    return false;
}

Notice the first one. That is atSetpoint() from the previous lesson, moved here unchanged, exactly as promised.

isFinished() is checked every cycle, and it is checked after execute(). A command that reports finished on its very first check still gets one execute() call. You will prove that in the challenges.

4 end and the interrupted flag

end() takes a boolean, and that boolean is information you cannot get anywhere else.

ValueMeans
interrupted == falseYou finished normally. isFinished() returned true
interrupted == trueSomething stopped you: the button was released, another command took the mechanism, or the robot was disabled

Those two cases often deserve different handling. "The arm reached the setpoint" and "the driver let go halfway" are not the same event, and end() is the only place you can tell them apart.

The rule that never changes

Stop the motor in end(), on both paths. It is the only method guaranteed to run when a command stops. Forgetting it is how a mechanism keeps driving after its command has been interrupted, which is a genuinely dangerous bug.

5 What the scheduler does in one tick

One call to CommandScheduler.getInstance().run() is one 20 millisecond tick of the robot. Inside it, in this order:

one tick
1. every registered Subsystem's periodic()            // next lesson
2. poll the controller buttons and triggers           // Unit 8
3. for each scheduled Command:
       execute()
       if (isFinished()) { end(false); unschedule it; }
4. schedule default commands for unused subsystems    // next lesson

Separately, and this catches people out: schedule(command) calls initialize() immediately, not on the next tick. By the time the first run() happens, initialization has already occurred.

PenguinSim prints its own view of this. Here is a short run with the scheduler's trace turned on.

scheduler trace
  [sim] CommandScheduler, one row per 20 ms robot loop.
   t(s)  cyc  subsystem periodic()   command execute()      isFinished()
  -----  ---  ---------------------- ---------------------- ------------
   0.00    -  >> SpinUpFlywheel.initialize()
   0.00    1  -                      SpinUpFlywheel         false
   0.02    2  -                      SpinUpFlywheel         false
   0.04    3  -                      SpinUpFlywheel         false
   0.06    4  -                      SpinUpFlywheel         false
   0.08    5  -                      SpinUpFlywheel         TRUE
   0.08    -  << SpinUpFlywheel.end(interrupted = false)
   0.10    6  -                      -                      -
   0.12    7  -                      -                      -

Read the timestamps. initialize() happened at 0.00 before cycle 1 existed. The command executed on cycles 1 through 5, reported finished on cycle 5, and ended at the same instant. From cycle 6 onward the scheduler is still running at full speed with nothing to do, which is the normal state of a robot between driver inputs.

Verify for current season

The ordering above is what this course teaches and what PenguinSim implements. Check the current WPILib documentation if you need to rely on the precise position of button polling relative to subsystem periodic(), since that detail has moved between versions. What has not changed is that execute() runs before isFinished() within a cycle, and that schedule() initializes right away.

6 Watch a flywheel spin up

Sim units

The real flywheel target is 4000 RPM, which is what the class above uses. PenguinSim reports degrees per second and its mechanism tops out near 80 at the 80 percent limit, so the sandbox targets 60 instead. The lifecycle is identical either way, and the lifecycle is the lesson.

output
[sim] SparkMax on CAN ID 5 (kBrushless) is alive.
initialize()   <-- once, at the start
  execute() #1    velocity =    0.00
  execute() #2    velocity =    9.60
  execute() #3    velocity =   18.05
  execute() #4    velocity =   25.48
  execute() #5    velocity =   32.02
  execute() #6    velocity =   37.78
  execute() #7    velocity =   42.85
  execute() #8    velocity =   47.31
  execute() #9    velocity =   51.23
  execute() #10   velocity =   54.68
  execute() #11   velocity =   57.72
  execute() #12   velocity =   60.39
  isFinished() -> TRUE
end(interrupted=false)   <-- once, at the stop
execute() ran 12 times.

That output is the entire lesson in one block.

  • initialize() printed once, before anything else.
  • execute() printed twelve times, once per tick.
  • isFinished() printed TRUE once, and only on the tick where the condition became true.
  • end() printed once, last.

Look at execute() #1. The velocity is 0.00, even though this cycle just commanded 0.8 output. That is not a bug. execute() reads the velocity before this tick's 20 milliseconds of motion have happened. Every reading you take in execute() describes the state at the start of the cycle. The flywheel needed twelve cycles, 240 milliseconds, and if you tried to shoot on cycle one you would fire into a stationary wheel.

7 The command that never ends

Now break it deliberately. Set TARGET to 100.0 and run it again.

output
  execute() #57   velocity =   79.94
  execute() #58   velocity =   79.95
  execute() #59   velocity =   79.95
  execute() #60   velocity =   79.96
Notice what did not happen

No isFinished() -> TRUE. No end(). No error, no warning, no exception. The command simply ran all sixty ticks and was still running when the loop stopped.

At 0.8 output the mechanism cannot exceed about 80, so a target of 100 can never be met. On a real robot this command runs forever, holding the flywheel, and anything sequenced after it never starts.

This is one of the hardest bugs in FRC to find, precisely because nothing goes wrong. Things just stop happening. The robot looks fine, the code is running, and the next step of your autonomous routine is waiting for a condition that will never be true.

The defence is a timeout, and the exercise below adds one.

Two more experiments worth running.

  • Set isFinished() to return false;. Same result. Sixty executes, no end(). This is what a "run while held" command looks like when nothing releases it.
  • Drop the output in execute() from 0.8 to 0.4. The ceiling halves, so a target of 60 also becomes unreachable. The end condition and the output are not independent choices.
You have written this shape twice already

In Relative vs. Absolute Encoders you wrote a homing routine that started, ran until it hit a hard stop, and finished. In PIDController in Code you wrote startMove(), moveToward() and atSetpoint().

Both times you invented this lifecycle by hand because the problem demanded it. All the framework does is agree on the names and call them for you on a reliable 20 millisecond schedule.

9 Common mistakes

Watch out for these
  • Thinking initialize() runs every cycle. Once, when the command starts. execute() is the every-cycle one.
  • Reading end() as "succeeded." It runs whenever the command stops. The interrupted flag is how you tell the two cases apart.
  • Treating return false as a bug. A command that never ends on its own is a valid design for behaviour that should run while a button is held.
  • Building a motor inside a command. Commands are handed their mechanism. Two objects for one motor means two things fighting over it.
  • Forgetting to stop the motor in end(). The mechanism keeps driving after the command is gone, and nothing tells you.
  • Assuming an unreachable end condition will error. Nothing errors. That silence is what makes it so hard to find.

The arm gets a command

Your Arm has startMove(), goToScore(), atSetpoint(), stop() and isHomed(). Nothing calls them on the right ticks. Write the command that does.

  1. Constructor takes an Arm and stores it. Do not create a motor inside the command.
  2. initialize() calls arm.startMove() to clear stale controller state.
  3. execute() runs one controller cycle toward the scoring setpoint.
  4. isFinished() is true when the arm is at the setpoint.
  5. end(boolean interrupted) stops the arm and prints a different message for each case.
  6. Bonus 1. Refuse to run when the arm is not homed. Finish immediately rather than driving to a setpoint that means nothing.
  7. Bonus 2. Add a timeout. If the arm has not arrived within 100 ticks, finish anyway. Something is jammed, and a command that runs forever is worse than one that gives up.

Working code prints this:

output
[sim] SparkMax on CAN ID 3 (kBrushless) is alive.
A) not homed:
  finished at 0.00 after 1 ticks
B) homed, run to completion:
  finished at 49.07 after 68 ticks
C) interrupted halfway:
  INTERRUPTED at 32.51 after 30 ticks

Case A is the point from section 3 made concrete. The command was finished before it started, and it still got exactly one execute().

Reveal the solution
ArmToScoreCommand.java · solutionJava
import edu.wpi.first.wpilibj2.command.Command;

public class ArmToScoreCommand extends Command {

    private final Arm arm;
    private static final int TIMEOUT_TICKS = 100;   // 2 seconds
    private int ticks = 0;

    // The command is HANDED the mechanism. It never creates hardware itself.
    public ArmToScoreCommand(Arm arm) {
        this.arm = arm;
    }

    @Override
    public void initialize() {
        ticks = 0;
        arm.startMove();          // clears stale integral and previous error
    }

    @Override
    public void execute() {
        ticks++;
        arm.goToScore();          // ONE controller cycle toward the setpoint
    }

    @Override
    public boolean isFinished() {
        if (!arm.isHomed()) {
            return true;          // Bonus 1: no known zero, no setpoint. Do not guess.
        }
        if (ticks >= TIMEOUT_TICKS) {
            System.out.println("  TIMED OUT, is something jammed?");
            return true;          // Bonus 2: give up rather than run forever
        }
        return arm.atSetpoint();
    }

    @Override
    public void end(boolean interrupted) {
        arm.stop();               // ALWAYS. This is the only guaranteed exit.
        System.out.printf("  %s at %.2f after %d ticks%n",
            interrupted ? "INTERRUPTED" : "finished", arm.getPosition(), ticks);
    }
}

Four things in that solution are worth more than the syntax.

  • The constructor takes the arm, it does not build one. If every command made its own motor object on CAN ID 3 you would have several objects issuing conflicting commands to one piece of hardware. This is the dependency injection idea from Phase 1 doing real work.
  • end() stops the arm on both paths. Not inside an if. Forgetting this is how a mechanism keeps driving after its command was interrupted.
  • The timeout is not decoration. Section 7 showed you a command that never finished and never complained. The timeout turns that silence into a printed message.
  • Bonus 1 returns true rather than throwing. A command that cannot safely do its job should end quietly, not crash the robot in the middle of a match.

Your command works. But Arm is still a plain class. Nothing stops two commands from grabbing it at the same time, and nothing runs its housekeeping when no command is scheduled. That is the next lesson.
