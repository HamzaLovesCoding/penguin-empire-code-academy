1 Why this matters

Everything you have built, in one command

Look at how little is left to invent.

In Unit 6 you learned that a controller needs an error and produces an output. In Unit 9 you got a drivetrain that accepts a rotation rate. In Unit 10 you got a camera that hands you an angle off target.

the entire design
error  = TX                        the camera already did the subtraction
output = pid.calculate(TX, 0.0)
       -> the drivetrain's rotation rate

Six lines of genuinely new code, standing on four units of work. That is what good structure feels like from the inside.

This loop drives 120 pounds of robot

The tuning warning from Unit 6 applies here with considerably more mass behind it. Bent parts and a mechanism coming off the robot were the consequences on an arm. This is the whole machine.

Start the gain small. The sandbox below exists so you can get the aggressive one out of your system somewhere harmless.

2 The setpoint is zero

Every controller in this course so far aimed at a position, such as 9.0 rotations. Here the target is always zero, because being aimed means having no angular error.

What moves instead is the measurement. TX changes as the robot turns and as the tag moves. You are not steering toward a number. You are cancelling an offset.

3 Sign conventions will bite you

Whether a positive TX means the tag is to the left or the right, and whether a positive rotation output turns the robot clockwise, both depend on how the camera was mounted and what the drivetrain's convention is.

Those two have to agree. If they do not, your robot turns away from the target, the error grows, the output grows, and you have built a positive feedback loop out of a 120 pound machine.

Do not reason about it. Test it.

Set the gain to something tiny like 0.01, run it, and watch which way it turns. If it turns away from the tag, negate the output.

This is exactly Unit 4's rule that you will not know which direction is positive until you test. Twenty minutes of reasoning about mounting orientation is twenty minutes you could have spent knowing.

You will produce this failure deliberately in the sandbox, where nothing can be damaged by it.

4 Losing the target

This is what separates working vision from a demo. From the previous lesson: TX reads zero with no target, which is indistinguishable from perfect alignment. So the command must ask whether the target is valid before it acts on any reading.

There are three sensible policies, and choosing one deliberately is the point.

PolicyBehaviourGood for
Stop and finishNo valid target, so stop the drivetrain and report finishedSimple, safe, and the default
Hold and waitKeep the last output briefly, hoping the tag reappearsBrief occlusions, such as a defender passing through
Stop but keep waitingStop moving, do not finish, keep lookingWhen a sequence must not advance without the tag

Teach yourself the first one as the default. The failure to avoid is the fourth option, which nobody chooses on purpose: carry on driving on a stale reading. That is what you get for free if you never think about this.

5 The command

commands/AimAtTagCommand.javaJava
import edu.wpi.first.math.controller.PIDController;
import edu.wpi.first.wpilibj2.command.Command;
import static frc.robot.Constants.VisionConstants;
import static frc.robot.Constants.RobotConstants;

public class AimAtTagCommand extends Command {

    private final DriveSubsystem     drive;
    private final LimelightSubsystem limelight;

    // Setpoint is ZERO. "Aimed" means no angular error.
    private final PIDController pid =
        new PIDController(VisionConstants.kAimP, 0.0, 0.0);

    public AimAtTagCommand(DriveSubsystem drive, LimelightSubsystem limelight) {
        this.drive     = drive;
        this.limelight = limelight;
        addRequirements(drive);       // NOT the limelight. reading it does not own it.
    }

    @Override
    public void initialize() {
        pid.reset();
        pid.setTolerance(VisionConstants.kAimToleranceDeg);
    }

    @Override
    public void execute() {
        if (!limelight.isTargetValid()) {
            drive.stopRotation();     // no valid tag: do not act on a stale reading
            return;
        }
        double tx  = limelight.getAngleToTag();     // the error, straight from the camera
        double out = pid.calculate(tx, 0.0);
        double max = RobotConstants.kMaxOutput;
        drive.rotate(Math.max(-max, Math.min(max, out)));
    }

    @Override
    public boolean isFinished() {
        // Finish when aimed, OR when there is nothing to aim at.
        return !limelight.isTargetValid() || pid.atSetpoint();
    }

    @Override
    public void end(boolean interrupted) {
        drive.stopRotation();         // always
    }
}

Four things in that class are worth more than the rest.

  • addRequirements(drive) and not the Limelight. Reading a sensor does not require exclusive ownership of it. Requiring the camera would stop any other command from reading vision at the same time, for no benefit. People over-require, and this is the clearest example of why not to.
  • The validity guard appears in both execute() and isFinished(). That is not redundant. One stops the motion, the other stops the command, and they are different jobs.
  • The clamp is here too. Every PID output in this course gets clamped, and a controller aiming a whole robot is not the place to start making exceptions.
  • end() stops rotation unconditionally, on both paths, as always.
Verify for current season

drive.rotate(double) and drive.stopRotation() are named here for readability. They are stand-ins for whatever your generated swerve subsystem actually exposes, which differs between the two generators and between versions of each. Substitute the real calls from your own drive subsystem.

Everything else in that class, meaning the controller, the guard, the clamp and the lifecycle, is yours and does not change.

6 Aim it, then break it

The fake is deliberately visible

PenguinSim has no camera and no drivetrain. So the sandbox defines a small FakeField in the file you are reading, labelled, rather than hiding it in the simulator.

That is on purpose. A visible fake is honest and you can see exactly what it assumes. An invisible one teaches you an API that does not exist. What is real here is the control loop, which is the part that transfers to the robot unchanged.

Read the two columns together. TX shrinks toward zero and the output shrinks with it, exactly like the arm in Unit 6. The output is pinned at the clamp for the first few ticks while the error is large, then comes off it as the robot closes in. Nothing here is a new idea.

Seventeen ticks instead of thirty three, because the output stayed on the clamp much longer. Same tuning skill from Unit 6, new mechanism. Keep raising it and you will find the same overshoot and chatter you found on the arm.

Experiment 2 · the sign error

This is what a sign error looks like

TX goes up and keeps going up, and the output stays pinned at full clamp the whole way. The controller is driving the error larger, and the larger it gets the harder it pushes.

On a real robot that is a 120 pound machine spinning up to its maximum rate while your code believes it is correcting. It does not stop, because nothing in the loop can ever be satisfied.

Test at a tiny gain and watch which way it turns before you trust it. Every time.

Experiment 3 · lose the target

Set tagId to 3, which is not one of ours.

output · foreign tag
kP = 0.05   starting tx = 25.00
tick      tx   output   aimed
tick 1  NO VALID TARGET, stopping

It refuses to move at all. The tag is right there, TX is a perfectly good 25 degrees, and the robot correctly declines to aim at it. Setting hasTarget = false produces the same result for a different reason, which is the behaviour you want.

7 TY for range

Same shape, one paragraph, because there is genuinely nothing new in it.

A second PIDController runs on TY with a non-zero setpoint, which is whatever TY reads at your preferred shooting distance. Its output drives forward and backward translation instead of rotation. Two controllers, two axes, running at the same time on one drivetrain.

The only genuinely new thing is that the setpoint is not zero, because "the right distance" is a particular TY reading rather than the absence of error. You measure it once by putting the robot where you want it and writing down what TY says.

Where this command actually gets used

An aiming command is rarely bound to a button on its own. It goes at the front of a scoring sequence: aim, then raise the arm, then score. That is a sequential group and you already know how to build one.

In Unit 11 the same command appears inside the autonomous routine, unmodified. One class, written once, reused twice. That is the composition payoff you were promised in Unit 3.

9 Common mistakes

Watch out for these
  • Reasoning about the sign instead of testing it. Set a tiny gain, run it, watch which way it turns. Two minutes instead of twenty.
  • Acting on a reading without checking it is valid. TX reads zero with no target, which looks exactly like being aimed.
  • Requiring the camera subsystem. Reading a sensor does not need exclusive ownership, and requiring it blocks every other command that wants to look.
  • Skipping the clamp because the drivetrain feels different. It is more mass, not less reason to clamp.
  • Setting the tolerance too tight. Ask for a tenth of a degree and the robot hunts forever without ever reporting itself aimed.
  • Forgetting the tag ID filter. Aiming at the other alliance's tag is a real failure and it looks like the code working perfectly.
Build it · PenguinBot

PenguinBot aims itself

PenguinBot has a LimelightSubsystem that can say where a tag is and whether it is one of ours. Nothing turns the robot toward it.

  1. Add kAimP to VisionConstants, starting small.
  2. Write AimAtTagCommand with the four lifecycle methods, the validity guard in both places, and the clamp.
  3. Write the test procedure you would follow the first time you run it on a real robot, including what gain you start at and what you are watching for.
  4. Put it at the front of a scoring sequence: aim, then the existing ScoreSequence.
  5. Bonus 1. Add a second controller on TY for range, with a non-zero setpoint. Say where that setpoint number comes from.
  6. Bonus 2. Add a timeout, so a robot that can never quite satisfy the tolerance does not hold the drivetrain for the rest of the match.
Reveal the solution

The command is the one in section 5, plus the timeout from Unit 7.

Constants.java · VisionConstantsJava
public static final class VisionConstants {
    public static final String kLimelightName   = "limelight";
    public static final double kAimToleranceDeg = 1.0;
    public static final int[]  kScoringTagIds   = { 7, 8 };   // VERIFY THIS SEASON

    // Start small. Raise it only after watching which way the robot turns.
    public static final double kAimP        = 0.02;
    public static final int    kAimTimeoutTicks = 100;        // 2 seconds
}

The first-run test procedure

  1. Robot on blocks, tag on a stand well off to one side so TX is clearly non-zero.
  2. Set the gain to 0.01. Deliberately far too low to be useful.
  3. Enable and schedule the command. Watch which way the modules turn. That is the only thing you are testing.
  4. If it turns away from the tag, negate the output and repeat step 3. Do not proceed until the direction is right.
  5. Raise the gain gradually, using the recipe from Unit 6, until it aims cleanly with no overshoot and no direction reversals.
  6. Cover the camera mid-aim and confirm the robot stops instead of continuing.
  7. Show it a tag that is not in kScoringTagIds and confirm it refuses to move.
  8. Only then put it on the floor.

Steps 3 and 4 are the entire reason this procedure exists. Everything else is tuning you already know how to do.

The scoring sequence, with aiming on the front

commands/AimAndScore.javaJava
import edu.wpi.first.wpilibj2.command.SequentialCommandGroup;

public class AimAndScore extends SequentialCommandGroup {

    public AimAndScore(DriveSubsystem drive, LimelightSubsystem limelight,
                       ArmSubsystem arm, IntakeSubsystem intake) {
        addCommands(
            new AimAtTagCommand(drive, limelight),   // face the tag first
            new ScoreSequence(arm, intake)           // then the cycle from Unit 8
        );
    }
}

Nine lines, and neither of the two commands inside it needed a single change. That is what composition buys you.

Bonus 1, where the TY setpoint comes from. You measure it. Put the robot exactly where you want it to shoot from, read TY, and write that number down as the setpoint. There is no formula, because it depends on how high the camera is mounted and at what angle. That is why it lives in Constants with a comment saying how it was obtained.

Bonus 2, why the timeout matters here specifically. An aiming command that can never satisfy its tolerance holds the drivetrain, and the drivetrain is the one subsystem the driver needs back. Without a timeout, a robot that is nearly-but-not-quite aimed refuses to be driven for the rest of the match.

PenguinBot can now find a tag and turn to face it. In the next unit that same command goes into an autonomous routine, unchanged, and the robot does it with nobody touching a controller.
