Relative vs. Absolute Encoders

1 Why this matters

Nine rotations from where?

Last lesson ended with the arm reporting 9.00 rotations. Now turn the robot off and turn it back on. The arm has not moved a millimetre. It is still physically holding a game piece in the air. getPosition() now returns 0.00.

Nothing broke. That is exactly what a relative encoder does. On startup it calls wherever it happens to be zero. The arm's position did not change. The reference did.

Now run code that says "go to 9.0" believing 0 is stowed. The arm drives another nine rotations past the top of its travel and into the frame. This costs nothing to prevent and everything to discover at a competition.

2 Two kinds of encoder

REV's own documentation puts the distinction well: incremental encoders measure a change in position as a mechanism rotates, and absolute encoders report an exact position at any time, including at startup.

Relative (incremental)Absolute
On startupReports 0, wherever it physically isReports its real position, for example 50 degrees
What it measuresChange since it started countingThe actual angle of the shaft it is on
Use it whenThere is a known starting position you can drive toThere is no physical stop to home against
The riskIts zero is meaningless until you establish oneIf the mechanical link to the mechanism fails, the reading stays plausible and stops being true
Where you get oneBuilt into every Neo and every Kraken. FreeA separate sensor, wired and mounted

PenguinBot's arm uses the Neo's built in encoder, which is relative. That is the common case, and it is why the rest of this lesson is mostly about homing.

3 Choosing between them

One question decides it: is there a physical place you can drive the mechanism to and know exactly where it is?

  • Yes. An arm that rests against a hard stop, an elevator that bottoms out, an intake that folds against the frame. Use the relative encoder you already have, and home it.
  • No. A turret that spins continuously, a swerve module's steering that can face any direction with no stop in either. Use an absolute encoder, because there is nowhere to home to.

That second case is not hypothetical. Swerve steering is exactly why absolute encoders show up on this robot at all, and Unit 9 comes back to it.

Wiring, briefly

On a SparkMax the two kinds arrive on different ports. The Neo's built in encoder must be connected to the encoder port, and REV documents absolute encoders as connecting through the data port, needing SparkMax firmware 1.6.0 or newer. REV also notes that reading incremental and absolute feedback from a single encoder through the SparkMax is not supported. In code you reach them with different calls: getEncoder() for the built in relative one and getAbsoluteEncoder() for an absolute one on the data port.

4 Homing a relative encoder

Homing means deliberately moving a mechanism to a place you know, and then declaring that place to be zero. Three steps, and none of them are optional.

Arm.javaJava
// 1. drive SLOWLY toward the known place
pivot.set(-0.15);

// 2. wait until it gets there and settles
//    (a timer, a current spike, or a limit switch, depending on the mechanism)

// 3. stop, then declare this spot zero
pivot.set(0);
pivot.getEncoder().setPosition(0);

Two details carry all the weight.

Slowly. You are driving a mechanism into a hard stop on purpose. At 15 percent output that is a gentle press. At 90 percent it is an impact, and homing is how teams break the very stop they are homing against. The 80 percent rule from Unit 4 is a ceiling, not a target, and homing wants to be far below it.

Stop before you zero. If the mechanism is still moving when you call setPosition(0), you have zeroed a place the arm was passing through rather than the place it rests. Everything downstream is then off by that amount.

5 Watch a power cycle happen

This runs the whole story: raise the arm, power cycle the robot, home it, then raise it again. Read the four printed lines carefully.

output
[sim] SparkMax on CAN ID 3 (kBrushless) is alive.
before power cycle: position =  10.59
[sim] SparkMax on CAN ID 3 (kBrushless) is alive.
after  power cycle: position =   0.00
after  homing:      position =   0.00
raised 25 cycles:   position =   8.72

Line two and line three print the same number. That is the lesson.

  • Line 2 is zero because the code restarted. The arm is still up. Nothing measured anything. The reading is a coincidence of when the program started.
  • Line 3 is zero because you put the arm somewhere you know and said so. Same number, entirely different meaning. Now 8.72 in line four is a real distance from a real place.
Two experiments worth running
  • Comment out the setPosition(0) line. Line three now prints -6.85, and every number after it is measured from a place with no meaning. This is what a robot with no homing routine does all match.
  • Change the homing speed to -0.9. The over 80 percent warning fires, and the final position comes out negative, because the arm was still travelling downward when you declared zero. Homing fast does not just risk the hardware. It gives you a wrong zero.

6 How an absolute encoder fails

Absolute encoders solve the startup problem and introduce a quieter one.

An absolute encoder reports the angle of the shaft it is mounted on. If the coupler slips, the belt snaps, or the motor free spins after a mechanical failure, the sensor keeps reporting its own angle perfectly and that angle no longer describes the mechanism.

The symptom is a reading that looks entirely reasonable and is wrong. A relative encoder that has lost its reference usually looks obviously broken. An absolute one that has lost its coupling looks fine. That is worse, because your code believes it.

relative encoder
Reports change since startup. Reads zero on boot no matter where the mechanism is.
absolute encoder
Reports the real angle of its shaft at all times, including on boot.
homing
Driving a mechanism to a known place and declaring that place zero.
setPosition(double)
The call that tells a relative encoder what number the current spot should be.
hard stop
A physical limit a mechanism can rest against. The thing homing homes to.

8 Common mistakes

Watch out for these
  • "The encoder is broken, it says 0 and the arm is up." It is working perfectly. A relative encoder reports change from startup, not absolute position. The reference needs establishing, and that is your job.
  • Thinking absolute encoders are strictly better. They cost money, need mounting and wiring, and fail in a way that looks plausible. A relative encoder with a homing routine is the right answer for most mechanisms.
  • Homing fast. You are driving a mechanism into a hard stop on purpose. Do it slowly or you break the stop, and you get a wrong zero into the bargain because the mechanism is still moving when you declare it.
  • Zeroing while the mechanism is moving. Stop first, then call setPosition(0).
  • Homing once and never again. Anything that can slip should be re-homed after it slips. If the arm gets hit hard in a match, its zero is a guess again.
Build it · PenguinBot

Arm.home()

Last lesson you gave PenguinBot an Arm class that reports position and velocity. Right now those numbers are measured from whenever the robot happened to boot. Fix that.

  1. Add home() to the Arm class. It drives the arm down slowly, waits for it to reach the stop, stops the motor, and zeroes the encoder.
  2. Use a slow speed. Something around -0.15. Far below the team's limit.
  3. Stop before you zero. The order of those two lines matters.
  4. Prove it works. Print the position before and after, and make the difference obvious.
  5. Bonus. Add isHomed() returning a boolean, set true by home(), so the rest of the robot can refuse to run the arm until it has been homed.
Reveal the solution
Arm.java · home()Java
private boolean homed = false;

public void home() {
    // 1. creep down toward the hard stop
    setSpeed(-0.15);
    for (int t = 1; t <= 40; t++) PenguinSim.step();

    // 2. stop BEFORE zeroing, so the arm is actually at rest
    stop();
    PenguinSim.step();

    // 3. declare this spot zero
    pivot.getEncoder().setPosition(0);
    homed = true;
}

public boolean isHomed() {
    return homed;
}

On a real robot that for loop is wrong, and it is worth knowing why now. Waiting a fixed number of cycles works in a simulator where nothing varies. On a real arm the right end condition is a limit switch closing, or the current spiking as the mechanism presses into the stop, or the velocity dropping to zero while you are still commanding movement. All three are end conditions, which means all three belong in a command. Unit 7 turns this into HomeArmCommand.

The isHomed() flag matters more than it looks. It lets RobotContainer refuse to run any arm setpoint until homing has happened, which turns "we forgot to home it" from a broken mechanism into a command that does nothing.

PenguinBot's arm can now report where it is and knows what zero means. Unit 6 uses both of those to make it actually stop at a setpoint instead of slamming past.
