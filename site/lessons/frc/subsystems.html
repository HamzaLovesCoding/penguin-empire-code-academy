Unit 7

Subsystem Anatomy

A subsystem owns a piece of the robot. Nothing else is allowed to touch that hardware, and the framework will enforce it for you rather than asking everyone to remember.

1 Why this matters

The ChairBot had four motors and two methods

The ChairBot's drivetrain had two sides, two wheels per side, and two motors driving each side. Four motors for one drivetrain.

The code declared four SparkMax variables at the top of a single class and exposed exactly two methods at the bottom: setLeftMotors(double) and setRightMotors(double).

Every subsystem has that shape. Variables at the top, methods at the bottom that take a value and apply it to the motors. Nothing outside that class knew the ChairBot had four motors. Add a fifth, or swap a SparkMax for a Kraken, and every caller stays exactly the same.

You have already seen this pay off. In Unit 6 your Arm quietly gained a follower motor and not one caller noticed or had to change.

2 The verified anatomy

Four numbered parts, always in this order.

Verified syntax · WPILib
IntakeSubsystem.javaJava
import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;
import edu.wpi.first.wpilibj2.command.SubsystemBase;

public class IntakeSubsystem extends SubsystemBase {

    // 1) declare the hardware
    private final SparkMax roller = new SparkMax(2, MotorType.kBrushless);

    // 2) constructor sets things up
    public IntakeSubsystem() {
    }

    // 3) your own methods, the ONLY place these motors get touched
    public void runRoller(double speed) { roller.set(speed); }
    public void stop()                  { roller.set(0); }

    // 4) periodic() runs every 20 ms, always
    @Override
    public void periodic() {
    }
}

Two words on that motor declaration carry the design.

  • private means nothing outside this class can reach the motor. The ownership rule from Unit 3 is now enforced by the Java compiler rather than by everyone remembering it.
  • final means the subsystem owns exactly one roller and will never point at a different one.

3 What extends SubsystemBase gets you

Three things. Most people cannot name any of them, which is why subsystems feel like boilerplate until they are not.

Registration

Constructing a SubsystemBase registers it with the CommandScheduler. That is why periodic() runs at all. Nobody calls it. The scheduler does, every tick, forever, whether or not any command is scheduled. You will watch this happen in section 6.

Requirements

A command can declare which subsystems it needs. The scheduler then guarantees that only one command uses that mechanism at a time.

ArmToScoreCommand.javaJava
public ArmToScoreCommand(ArmSubsystem arm) {
    this.arm = arm;
    addRequirements(arm);     // nobody else drives the arm while this runs
}

Schedule a second command that also requires the arm and the first one is interrupted. Its end(true) runs, it is unscheduled, and the new command takes over. That is the framework enforcing Unit 3's ownership rule at runtime instead of by convention.

Leave addRequirements out and both commands run at once. Both call set() on the same motor on the same tick, and the mechanism judders as it receives two different outputs fifty times a second. Nothing errors.

Default commands

A subsystem can name a command to run whenever nothing else is using it. That is how a drivetrain keeps responding to the joysticks while no other command has claimed it. Unit 8 is where this becomes useful.

Verify for current season

SubsystemBase, addRequirements and setDefaultCommand are not in our curriculum's verified boxes, and the base type has been reorganised across WPILib versions. Check the current documentation for exact signatures. The four-part anatomy above is verified.

PenguinSim does not implement addRequirements, so the sandbox below cannot demonstrate interruption. Read the requirements section as code, not as something to run here.

4 periodic versus execute

Last lesson warned you these get confused. Now that both exist in your code, here is the difference laid out.

periodic()execute()
Belongs toThe SubsystemThe Command
RunsAlways, every tickOnly while that command is scheduled
Good forTelemetry, safety limits, housekeepingDoing the actual job
How manyOne per subsystemOne per command
The rule of thumb

If it should happen whether or not anyone asked for it, it goes in periodic(). Publishing the arm's position to the dashboard is periodic(). Driving the arm to a setpoint is execute().

Do not set motors in periodic()

If periodic() writes to the motor every tick, it fights every command that also writes to it. Both run on the same tick, the last one wins, and which one is last depends on registration order. The mechanism behaves inconsistently and nothing in the code looks wrong.

periodic() observes. Commands act. The one honest exception is a guarded safety cut-off that can only ever stop the mechanism, never drive it, and the exercise builds one.

5 Exactly one instance

Subsystem methods are not static, so you need an instance. You call arm.goToScore(), never ArmSubsystem.goToScore(). That is the same distinction you met in Phase 1.

The rule that matters here is stronger than that. Exactly one instance per mechanism, created in RobotContainer, handed to every command that needs it.

Two subsystem objects means two motor objects

Write new ArmSubsystem() in two places and you have two objects, each holding its own SparkMax(3, ...), both issuing commands to one physical motor. Requirements will not save you, because the scheduler sees two different subsystems and has no idea they share hardware.

It compiles perfectly. Both periodic() methods run. The motor receives conflicting outputs and you will spend an afternoon on it.

Four things are proven in that output.

  • periodic() ran on ticks 1, 2 and 3, before any command existed. This is the headline. Registration happened inside the SubsystemBase constructor, so from the moment the object existed the scheduler was calling it.
  • Within every tick, periodic() printed before execute(). Every time, without exception. That is the scheduler order from the last lesson, confirmed.
  • initialize() printed before tick 4's periodic(). Scheduling initializes immediately, not on the next tick.
  • periodic() kept running on ticks 72 to 75, after the command ended. The subsystem is always awake. The command was a visitor.
Why the position keeps rising after end()

Look at ticks 72 through 75. The command has ended and called stop(), and the arm is still moving: 49.16, 49.25, 49.32, 49.39. It eventually settles at 49.73 and stops there.

That is not a bug and periodic() is not driving anything. stop() sets the output to zero, which removes the push. It does not apply a brake. The mechanism has momentum and coasts until friction takes it. Real mechanisms do the same, which is one reason an arm that stops exactly on target in the shop can overshoot slightly on a robot carrying more weight.

9 Common mistakes

Watch out for these
  • Thinking periodic() only runs when a command is using the subsystem. It runs every tick from construction onward. The sandbox proved it before any command existed.
  • Setting motors in periodic() because it is convenient. It then fights every command that also sets that motor.
  • Treating addRequirements as boilerplate. It is the only thing stopping two commands from driving one mechanism.
  • Creating a subsystem inside a command. One instance per mechanism, made in RobotContainer and handed around.
  • Calling subsystem methods on the class name. They are not static. You need the instance.
  • Making the motor field public. Then anything can reach past your methods and set it directly, and every guarantee your class makes is void.
Build it · PenguinBot

PenguinBot gets real subsystems

Intake from Unit 4 and Arm from Units 5 and 6 are still plain classes. Promote both.

  1. IntakeSubsystem extends SubsystemBase: roller on CAN ID 2, with runRoller(double), intake(), outtake() and stop(). Give it a periodic() that prints the roller's commanded speed.
  2. ArmSubsystem extends SubsystemBase: everything your Arm already does, plus a periodic() that prints position and whether it is homed.
  3. Update ArmToScoreCommand to take an ArmSubsystem and call addRequirements(arm).
  4. Write down where the single instance of each subsystem will be created, and why there must be exactly one.
  5. Bonus. Add a safety guard in ArmSubsystem.periodic() that stops the motor if the position goes past 12.0 rotations, and write a comment explaining why this is the rare acceptable case of periodic() touching a motor.
Reveal the solution
subsystems/ArmSubsystem.javaJava
import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;
import edu.wpi.first.math.controller.PIDController;
import edu.wpi.first.wpilibj2.command.SubsystemBase;

public class ArmSubsystem extends SubsystemBase {

    // 1) hardware at the top
    private final SparkMax pivot    = new SparkMax(3, MotorType.kBrushless);
    private final SparkMax follower = new SparkMax(4, MotorType.kBrushless);

    public  static final double SCORE_POSITION  = 9.0;
    public  static final double STOWED_POSITION = 0.0;
    private static final double TOLERANCE       = 0.25;
    private static final double MAX_OUTPUT      = 0.8;
    private static final double SAFETY_LIMIT    = 12.0;

    private final PIDController pid = new PIDController(0.2, 0.0, 0.0);
    private boolean homed = false;

    // 2) constructor
    public ArmSubsystem() {
        pid.setTolerance(TOLERANCE);
    }

    // 3) methods, the ONLY place these motors get touched
    public double  getPosition() { return pivot.getEncoder().getPosition(); }
    public boolean isHomed()     { return homed; }
    public boolean atSetpoint()  { return pid.atSetpoint(); }
    public void    startMove()   { pid.reset(); }

    public void setSpeed(double speed) {
        double safe = Math.max(-MAX_OUTPUT, Math.min(MAX_OUTPUT, speed));
        pivot.set(safe);
        follower.set(safe);
    }

    public void stop() {
        pivot.set(0);
        follower.set(0);
    }

    public void moveToward(double setpoint) {
        if (!homed) { stop(); return; }
        setSpeed(pid.calculate(getPosition(), setpoint));
    }

    public void goToScore()  { moveToward(SCORE_POSITION);  }
    public void goToStowed() { moveToward(STOWED_POSITION); }

    public void finishHoming() {
        stop();
        pivot.getEncoder().setPosition(0);
        homed = true;
    }

    // 4) periodic, every 20 ms, always, command or no command
    @Override
    public void periodic() {
        System.out.printf("  arm: pos %6.2f  homed %b%n", getPosition(), homed);

        // The rare case where periodic() may touch a motor.
        // This is a hard safety limit, not control. It can only ever STOP the
        // mechanism, never drive it, so it cannot fight a command for position.
        // It can only overrule one that has already gone wrong.
        if (getPosition() > SAFETY_LIMIT) {
            stop();
        }
    }
}
commands/ArmToScoreCommand.javaJava
import edu.wpi.first.wpilibj2.command.Command;

public class ArmToScoreCommand extends Command {
    private final ArmSubsystem arm;

    public ArmToScoreCommand(ArmSubsystem arm) {
        this.arm = arm;
        addRequirements(arm);     // no other command may drive the arm while this runs
    }

    @Override public void initialize()    { arm.startMove(); }
    @Override public void execute()       { arm.goToScore(); }
    @Override public boolean isFinished() { return !arm.isHomed() || arm.atSetpoint(); }
    @Override public void end(boolean interrupted) { arm.stop(); }
}

Where the instances live. Exactly one ArmSubsystem and one IntakeSubsystem, both created as fields in RobotContainer, which is the subject of Unit 8. Each one is handed into every command's constructor. One mechanism, one owner, one object.

Why the safety guard is allowed. The rule says periodic() must not set motors, and this sets a motor. The reason it is acceptable is in the comment: it can only ever call stop(), never drive to a position. It cannot compete with a command over where the arm should be, because it has no opinion about where the arm should be. It only has an opinion about where the arm must not go. Learn the reasoning, because "never do X" rules with real exceptions are only useful if you know which exceptions are real.

IntakeSubsystem is deliberately left to you. It is the same shape with less in it, and writing the second one from scratch is where the pattern actually sticks.
