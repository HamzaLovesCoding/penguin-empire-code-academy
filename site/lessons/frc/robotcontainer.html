1 Why this matters

Six steps from a thumb to a motor

Unit 3 promised you this trace. Every single thing in it now exists in your code.

the full signal flow
1. CommandPS5Controller, mapped to Driver Station port 0.
2. Button pressed, its state changes to true.
3. onTrue fires an InstantCommand.
4. The InstantCommand's lambda calls intake.runRoller(0.7).
5. Inside runRoller, .set(0.7) is applied to the motor.
6. The motor runs at that speed until something changes it.

From step 6 the hardware path from Unit 1 takes over. The roboRIO puts a message on the CAN bus, the SparkMax receives it, and the Neo spins.

That is the basic loop. Everything advanced in the rest of this course sits on top of it.

There is a second reason this file exists, and it is more basic than the first. Subsystem methods are not static. You cannot write ArmSubsystem.goToScore(). You need an instance, and this is the file where the robot's objects live.

2 The three sections

  • Top. Declare the subsystems, the controller, and any commands you want to reuse.
  • Constructor. Set up dashboard widgets and the autonomous picker, then call configureBindings().
  • configureBindings(). Map controller buttons to commands.

Nothing is generated in this file and nothing is processed in it. Everything is connected in it. It runs once at startup and then sits still.

3 Where instances are born

One ArmSubsystem. One IntakeSubsystem. One controller. Created as fields here, and handed into every command's constructor.

Unit 7 showed you what goes wrong otherwise. Two ArmSubsystem objects means two SparkMax(3, ...) objects fighting over one motor, and it compiles perfectly. RobotContainer being the single place they are constructed is what prevents that from ever happening.

Why the ordering in this file is not arbitrary

A binding like () -> intake.runRoller(0.7) captures the intake field. The subsystem instance has to exist before the binding that refers to it is written, which is why the declarations sit at the top and configureBindings() is called from the constructor rather than earlier.

4 InstantCommand

Unit 3 said some behaviour is instantaneous and does not need a command class of its own. InstantCommand is how that behaviour gets to be a command anyway, so it can be bound to a button and dropped into a sequence.

It runs its action once and immediately reports finished. That second half matters more than it looks: because it ends straight away, the next step of a sequence fires immediately after it.

the smallest command there isJava
import edu.wpi.first.wpilibj2.command.InstantCommand;

new InstantCommand(() -> intake.runRoller(0.7));

The () -> is the lambda from Phase 1, and here it means exactly one thing: run this line when the command starts.

6 The whole file

RobotContainer.javaJava
package frc.robot;

import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.InstantCommand;
import edu.wpi.first.wpilibj2.command.button.CommandPS5Controller;

import frc.robot.subsystems.ArmSubsystem;
import frc.robot.subsystems.IntakeSubsystem;
import frc.robot.commands.ArmToScoreCommand;
import static frc.robot.Constants.OperatorConstants;
import static frc.robot.Constants.IntakeConstants;

public class RobotContainer {

    // ---- TOP: the robot's objects. One instance each. --------------------
    private final ArmSubsystem    arm    = new ArmSubsystem();
    private final IntakeSubsystem intake = new IntakeSubsystem();

    private final CommandPS5Controller driver =
        new CommandPS5Controller(OperatorConstants.kDriverControllerPort);

    // ---- CONSTRUCTOR: wire it up, once, at startup -----------------------
    public RobotContainer() {
        configureBindings();
    }

    // ---- BINDINGS: inputs in, commands out -------------------------------
    private void configureBindings() {

        // A behaviour with an end. Fire and forget.
        driver.cross().onTrue(new ArmToScoreCommand(arm));

        // Lives and dies with the button.
        driver.square().whileTrue(
            new InstantCommand(() -> intake.runRoller(IntakeConstants.kIntakeSpeed)));

        driver.circle().whileTrue(
            new InstantCommand(() -> intake.runRoller(IntakeConstants.kOuttakeSpeed)));

        // One instantaneous action, latched on a single press.
        driver.triangle().onTrue(new InstantCommand(() -> {
            intake.stop();
            arm.stop();
        }));
    }

    public Command getAutonomousCommand() {
        return null;   // Unit 11 fills this in
    }
}

Read the shape rather than the details. Two subsystem fields, which are the instances for the entire robot. A controller whose port comes from Constants. Four bindings, each with a condition chosen for a reason. One stub with a forward pointer.

RobotContainer also holds the autonomous picker. It is a dashboard widget that lets the drive team choose which routine runs, and getAutonomousCommand() is what Robot.java calls to get it. Unit 11 builds it.

Verify for current season

Current WPILib lets you pass subsystem requirements to InstantCommand alongside the action, which is worth doing so the scheduler knows what each binding claims. It also offers factory methods on subsystems as a shorter way to build simple commands. Check what your season provides. new InstantCommand(runnable) is verified in our curriculum and works everywhere.

7 What does not go here

  • No motor objects. Those belong to subsystems, and only to subsystems.
  • No gains or setpoints. Those belong to Constants.
  • No per-cycle logic. Nothing in this file runs every 20 milliseconds. configureBindings() runs once and never again.

People put loops and motor calls in RobotContainer because it feels like the main file. It is not. It connects things and then stops.

8 Two mechanisms, no coordination

The sandbox fakes the controller

PenguinSim has no controller, so the bindings are stored as Runnable fields and fired by a faked-press loop. The RobotContainer structure itself is real, and so is everything the scheduler does with it.

Nothing in that file coordinates anything

The arm was still travelling when the intake turned on at tick 10 and off at tick 30, and neither disturbed the other. There is no code anywhere saying they are allowed to run together.

They do not conflict because they do not share a subsystem. The requirements system does the coordinating for you, and it does it by default. That is the payoff of Unit 7.

Two experiments worth running.

  • Press both at the same tick. Nothing changes. Different subsystems never compete.
  • Move new ArmSubsystem() inside ArmToScoreCommand's constructor so the command builds its own. The command's own arm moves, and the arm that RobotContainer is printing never budges. Two objects, one CAN ID, no error message.

10 Common mistakes

Watch out for these
  • Treating this as where the robot runs. It is where the robot is wired. It runs once at startup and nothing in it happens every 20 milliseconds.
  • Letting each command create the subsystem it needs. One instance, created here, handed in.
  • Treating InstantCommand as a workaround. It is the intended tool for instantaneous behaviour, and it is what makes a one-line action usable inside a sequence.
  • Writing a full Command class for everything. For behaviour with duration, yes. For setting a roller to 0.7, a lambda is the right amount of code.
  • Expecting two simultaneous presses to conflict. Only if they require the same subsystem.
  • Calling subsystem methods on the class name. They are not static, which is the whole reason this file exists.

PenguinBot becomes drivable

Every layer exists separately: subsystems, commands, constants and a binding plan. Nothing has ever connected them. Write the file that does.

  1. Fields. One ArmSubsystem, one IntakeSubsystem, one CommandPS5Controller on the port from Constants.
  2. Constructor calls configureBindings().
  3. Bindings. Cross raises the arm with onTrue, square intakes with whileTrue, circle outtakes with whileTrue, triangle is a panic stop with onTrue.
  4. A getAutonomousCommand() stub returning null, with a comment pointing at Unit 11.
  5. Below the code, write the six-step trace for pressing square, from thumb to roller, naming the class involved at each step.
  6. Bonus. Bind cross().onFalse(...) to an InstantCommand that stows the arm, so tapping cross raises it and releasing lowers it. Then explain why that is a bad binding for a scoring mechanism.
Reveal the solution

The file is the one in section 6. What matters is the trace.

The six-step trace for pressing square

  1. The driver presses square on the controller assigned to Driver Station port 0.
  2. CommandPS5Controller, created in RobotContainer with kDriverControllerPort, sees the state change to true.
  3. The whileTrue binding in configureBindings() schedules the InstantCommand.
  4. The InstantCommand's lambda runs intake.runRoller(IntakeConstants.kIntakeSpeed).
  5. IntakeSubsystem.runRoller, the only code in the project that touches this motor, calls roller.set(0.7).
  6. The SparkMax on CAN ID 2 drives the Neo and the roller spins until something changes it.

Steps 5 and 6 hand off to the hardware path from Unit 1: roboRIO, then CAN, then the SparkMax, then the Neo.

The bonus, and why it is bad. cross().onFalse(stowArm) means the arm drops the instant the driver's thumb leaves the button. During a scoring cycle the driver's hand is moving between buttons constantly, so the arm would slam down in the middle of a score. Raising and lowering are two deliberate actions and deserve two deliberate buttons. Better still, one command that does the whole cycle in order, which is the next lesson.

Four buttons, four behaviours. But scoring is really three things in order: arm up, then outtake, then arm down. One press should do all three. That is the next lesson.
