What P, I and D Do

1 Why this matters

A powerful ally and a dangerous foe

That is how our curriculum introduces PID, and both halves are earned.

Try to raise PenguinBot's arm to the scoring position with what you know now. Full power sails past and slams into the top of its travel. Gentle power might not lift the arm at all, and if it does, it keeps going and still slams into the top, just later. There is no value you can pass to set() that means "arrive at the scoring position and stop there."

That is open loop. The output has no idea what is happening. Closed-loop control fixes it with something close to trivial: look at how far away you are, and push in proportion to that. Far away, push hard. Close, push gently. At the target, stop pushing.

The foe half is real too. Every season this team has broken something with bad PID numbers, including bent parts and a mechanism that came off the robot. The same feedback that makes an arm arrive gently makes it hammer itself apart when the gains are wrong. The next lesson is about finding numbers that are not wrong.

2 Error is the whole idea

Two words carry this entire unit.

setpoint
Where you want the mechanism to be. For PenguinBot's arm, 9.0 rotations.
error
setpoint - current. How far off you are, and which way.

The current value comes from the encoder you learned to read in Unit 5. That is why Unit 5 came first. A controller with no measurement has nothing to compute an error from.

A controller's only job is driving error toward zero. Everything else on this page is a different strategy for doing that.

Keep the sign

Our curriculum reference writes error with absolute value bars around it, as e(t) = |target - current|. That describes the size of the error, which is fine when you are talking about how close you are.

Do not write it that way in code. A controller needs the direction as well as the size. If the arm is above the setpoint the error is negative, the output is negative, and the motor runs the other way. Strip the sign and the arm can only ever move one direction.

3 P, the proportional term

The proportional term is one multiplication.

the P term
output = kP * error

kP is a number you pick. It is called a gain. Large error gives large output, small error gives small output. The mechanism slows down as it approaches the target, and you never wrote a line of code that says "slow down near the end." It falls out of the multiplication.

Where P fails: at the very end. A tiny error times a small gain is a tiny output, and a tiny output may be less push than the mechanism's own friction. The arm creeps to just short of the setpoint and stops there. The gap that is left over is called steady-state error. You will watch it happen in the sandbox below.

4 I, the integral term

The integral term adds up error over time and pushes harder the longer you have failed to arrive.

That is what closes the gap P leaves behind. While the arm sits 1 degree short, that 1 degree keeps accumulating, the added output keeps growing, and eventually it is enough to break through friction or lift against gravity. Then the arm moves and the error goes to zero.

Where I fails: the accumulated push does not disappear the instant you arrive. It has to be unwound, and while it unwinds it carries the mechanism past the target. Too much I overshoots, then oscillates, then in bad cases never settles at all. This is called windup, and you will see a spectacular version of it next lesson.

5 D, the derivative term

The derivative term looks at how fast the error is changing and pushes against that change.

If the arm is closing on the setpoint quickly, D produces an output opposing the motion, which brakes the approach before it can overshoot. If the arm is barely moving, D contributes almost nothing.

Where D fails: too much D makes the response twitchy, and it can trade one big oscillation for tighter, faster ones. It can also leave a small offset.

The three terms in one line each
  • P looks at where you are.
  • D looks at how fast you are getting there.
  • I looks at how long you have been failing to arrive.
TermReacts toJobFailure mode
kPHow far off you are nowDo the bulk of the workToo small stalls short, too large overshoots
kIError added up over timeFinish the last bit that P cannotWinds up and carries past the target
kDHow fast the error is changingDamp the approachTwitchy response, can leave an offset
You will usually only need P

Most FRC mechanisms run on the P term alone. Our curriculum's own worked example is new PIDController(0.05, 0.0, 0.0), with I and D both zero.

Students arrive expecting all three terms to be mandatory. They are not. Starting with P alone and adding nothing else is the professional default, not a beginner shortcut. Add D only when the approach overshoots, and add I only when the mechanism reliably stops short.

6 A P controller in four lines

There is a WPILib class for this and you will meet it in two lessons. You do not need it. A complete P controller is four lines of arithmetic.

Arm.javaJava
// Closed loop, by hand. This is all a P controller is.
double error  = 9.0 - arm.getPosition();          // how far away am I, and which way
double output = 0.05 * error;                     // push in proportion to that
output = Math.max(-0.8, Math.min(0.8, output));   // the team's 80 percent rule
arm.setSpeed(output);

Line by line:

  • Line 2. 9.0 is the setpoint in rotations. arm.getPosition() is the encoder from Unit 5 finally earning its keep. Subtracting gives a signed error.
  • Line 3. 0.05 is kP. It is the only number you will tune for a while.
  • Line 4. This one is not optional, and it is the line people leave out. Read the callout below.
  • Line 5. The output goes straight into the motor, exactly like Unit 4. A PID output is a percent output, not a speed and not a position.
The controller does not know about your limits

A controller is arithmetic. It has no idea what a motor is, what the team's rules are, or that anything above 1.0 is meaningless.

Work it out. With kP = 0.2 and the arm sitting at 0.0 rotations, the error is 9.0 and the output is 0.2 * 9.0, which is 1.8. That is 180 percent output. The motor controller will cap it at 100 percent, which is already past the 80 percent rule Unit 4 gave you after this team destroyed a motor.

Clamping is your job, on every closed loop you write. That line appears in every PID sample in Units 6 through 11.

Here is the same thing written with the WPILib class, shown only so you recognise it later. The next two lessons explain it properly.

preview onlyJava
import edu.wpi.first.math.controller.PIDController;

PIDController pid = new PIDController(0.05, 0.0, 0.0);   // kP, kI, kD
double output = pid.calculate(arm.getPosition(), 9.0);   // (current, setpoint)

Same arithmetic. The class is convenience, not the concept. It still returns a number that needs clamping.

7 Race open loop against P control

This runs two motors side by side toward the same target. One just pushes. One measures first. Press Run, then read the two columns against each other.

The sandbox works in degrees

PenguinSim reports degrees, so the target here is 50.0 rather than the arm's real 9.0 rotations. A real REVLib encoder reports rotations and RPM, which is what every real-robot code block on this page uses. The gains below are tuned for the simulator's mechanism and are not PenguinBot's numbers. What transfers is the shape of the curves.

At kP = 0.02 you get this:

Three things to take from those columns.

  • The open-loop column climbs at a constant rate and never stops. It passes the target somewhere around tick 57 and just keeps going, ending at 82.67. On a real robot that column is the arm hitting the top of its travel and staying there with the motor still pushing.
  • The P column decelerates. It gains 13 in the third block of ten ticks and 0.12 in the last. Nobody wrote that. It is kP * error with a shrinking error.
  • The first ten ticks of both P runs are identical. Set kP to 0.05 and tick 10 still reads 7.53. At the start the error is 50, so the output is 1.0 at one gain and 2.5 at the other, and the clamp caps both at 0.8. That clamp is not decoration. It is actively holding the mechanism back.

Now change kP and run it again.

Set kP toWhat you seeWhat it proves
0.005Reaches only 29.50 by tick 90Too little P. The push shrinks faster than the distance does
0.02Glides in and stops on 49.99A gain that suits this mechanism
0.05Hits 48.86 at tick 40, peaks at 53.04, comes back to 49.65Too much P. It arrives faster and pays for it with overshoot

Leave kP = 0.005 running much longer and it stalls at 46.44 and stays there. The error is 3.56, the output is 0.005 * 3.56, which is 0.018, and that is less push than the mechanism's friction. This is steady-state error, and it is exactly what the I term exists to fix.

8 What this lesson does not cover

Two techniques sit next to PID and neither is taught in this course. You should know the names so you recognise them in other teams' code.

  • Motion profiling. Instead of aiming at the final target, you feed the controller a planned path of intermediate targets so the mechanism follows a controlled speed curve. This team skipped it because the syntax kept changing between seasons and the payoff did not justify the churn.
  • Feedforward. A calculated output added on top of PID based on what you know the mechanism needs, such as the constant push required to hold an arm against gravity. It handles the predictable part so PID only has to correct the rest.

There is also no calculus on this page and none is coming. The names of the terms come from calculus. The implementation is multiplication, addition and subtraction.

10 Common mistakes

Watch out for these
  • Assuming you need all three terms. Most mechanisms on this robot run on P alone. Add a term when a symptom demands it, not because the acronym has three letters.
  • Writing error with Math.abs. The sign is what tells the motor which direction to move. Take it away and the arm can only travel one way.
  • Treating the output as a speed or a position. It is a percent output. It goes straight into motor.set(), and it needs the same clamp everything else does.
  • Forgetting to clamp. kP = 0.2 at an error of 9 asks for 1.8. The controller has no idea that is unreasonable.
  • Calling the controller once. Closed loop means recomputing every cycle. One call sets one output for 20 milliseconds and then nothing further happens.
  • Expecting gains to transfer. Gains belong to one mechanism with its own weight, gearing and friction. The arm's numbers are not the drivetrain's numbers.
Build it · PenguinBot

An arm that reaches for a setpoint

After Unit 5 your Arm class can read its position and can home itself so that zero means stowed. It still cannot stop anywhere on purpose. Fix that, by hand, with no controller class.

  1. Constants. SCORE_POSITION, a TOLERANCE, and a MAX_OUTPUT of 0.8.
  2. getError(double setpoint) returning the signed error.
  3. atSetpoint(double setpoint), true when the error is inside the tolerance.
  4. moveToward(double setpoint), one cycle of the loop: measure, compute, clamp, set.
  5. Refuse to run when the arm is not homed. Stop the motor and return. A setpoint with an unknown zero is not a target, it is a hazard.
Read this before you write moveToward

moveToward is one cycle, not a journey. It does not contain a loop and it does not wait for anything. It computes one output and sets it. Something outside the class has to call it every 20 milliseconds. Calling it once moves the arm for 20 milliseconds and then stops. This is a very common misreading of closed-loop code.

Working code prints this:

output

Before homing:
  position = 0.00   homed = false
After homing:
  tick  20   position =  20.73   error =  29.27   atSetpoint = false
  tick  40   position =  40.63   error =   9.37   atSetpoint = false
  tick  60   position =  48.09   error =   1.91   atSetpoint = false
  tick  80   position =  49.87   error =   0.13   atSetpoint = true
  tick 100   position =  49.99   error =   0.01   atSetpoint = true
  tick 120   position =  49.99   error =   0.01   atSetpoint = true

Note the first block. Ten cycles of moveToward ran and the arm did not move at all, because it was not homed. That guard is the previous lesson paying off.

Reveal the solution

Real-robot version, with real imports and PenguinBot's real numbers in rotations.

Arm.java · solutionJava
import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;

public class Arm {
    private final SparkMax pivot = new SparkMax(3, MotorType.kBrushless);

    public static final double SCORE_POSITION  = 9.0;    // rotations
    public static final double STOWED_POSITION = 0.0;
    private static final double TOLERANCE  = 0.25;       // rotations
    private static final double MAX_OUTPUT = 0.8;        // the team's 80 percent rule

    private double kP = 0.05;                            // tuned properly next lesson
    private boolean homed = false;

    public double getPosition() { return pivot.getEncoder().getPosition(); }
    public void stop()          { pivot.set(0); }
    public boolean isHomed()    { return homed; }

    public void home() {
        pivot.getEncoder().setPosition(0.0);
        homed = true;
    }

    public void setSpeed(double speed) {
        pivot.set(Math.max(-MAX_OUTPUT, Math.min(MAX_OUTPUT, speed)));
    }

    // Signed on purpose. The sign is the direction to move.
    public double getError(double setpoint) {
        return setpoint - getPosition();
    }

    public boolean atSetpoint(double setpoint) {
        return Math.abs(getError(setpoint)) < TOLERANCE;
    }

    // Call this EVERY 20 ms while you want the arm to hold a setpoint.
    // Calling it once does almost nothing. Closed loop means repeatedly.
    public void moveToward(double setpoint) {
        if (!homed) {
            stop();                          // no known zero, no setpoint
            return;
        }
        setSpeed(kP * getError(setpoint));   // setSpeed already clamps
    }
}

Four things in that solution matter more than the syntax.

  • moveToward contains no loop. It is a single step. The loop lives outside, and in Unit 7 it becomes the robot's own 20 millisecond loop.
  • atSetpoint looks like a convenience method today. In Unit 7 it becomes a command's isFinished(), unchanged.
  • kP is a field rather than a constant, because you are about to spend an entire lesson changing it.
  • The clamp lives inside setSpeed, so no caller can bypass it. That is the same ownership rule from Unit 3, enforced by the language instead of by memory.

Your arm now reaches for a setpoint. Whether it arrives gently, slams into the stop, or shakes itself apart depends entirely on one number you have not chosen properly yet. That is the next lesson.
