1 Why this matters

The technique this team dropped, and why

Motion profiling is a more sophisticated way of moving a mechanism. Instead of reacting to the error you plan a smooth speed curve in advance and follow it. It is a real improvement for large moves.

This team tried it and stopped using it. Not because it was too hard, and not because it did not work. They stopped because the syntax changed between seasons and keeping up with a moving API cost more time than the technique returned.

That is a useful thing to hear early, because it frames what is worth learning. PIDController is worth learning because it is small, it is stable across seasons, and it is used on nearly every FRC robot. You will type new PIDController(kP, kI, kD) for years. Motion profiling you can look up in the season you actually need it.

Be clear about the honest answer: for a P-only controller your four lines are genuinely fine. The class earns its place the moment you want I, or D, or tolerance checking, or a teammate who can read what you wrote. On this team that is all four, so use the class.

3 The verified syntax

Verified syntax · WPILib
Arm.javaJava
import edu.wpi.first.math.controller.PIDController;

// Three doubles, in this order: kP, kI, kD
PIDController pid = new PIDController(0.05, 0.0, 0.0);

double current = motor.getEncoder().getPosition();
double output  = pid.calculate(current, 50.0);   // (measurement, setpoint)
motor.set(output);                               // a percent output, same as Unit 4

Four things to notice.

  • The constructor takes three doubles in the order kP, kI, kD. There are no names attached, only positions. Get the order wrong and it compiles perfectly and behaves strangely.
  • calculate takes the measurement first and the setpoint second. Section 4 is about what happens when you get that backwards, because it is the most common mistake on this page.
  • The output goes straight into set(). This is where Units 4, 5 and 6 join up. Encoder reading in, percent output out.
  • It still returns numbers outside the motor's range. Adopting the class does not remove your clamp.

Here is the same thing with PenguinBot's real numbers and the clamp Unit 6 has drilled into you.

Arm.javaJava
import edu.wpi.first.math.controller.PIDController;

// One controller, created once, tuned in the previous lesson.
private final PIDController armPid = new PIDController(0.2, 0.0, 0.0);

public void moveToward(double setpoint) {
    double output = armPid.calculate(getPosition(), setpoint);
    setSpeed(output);      // setSpeed clamps to 0.8. The controller will not.
}
The class has never heard of the 80 percent rule

With kP = 0.2 and the arm stowed at 0.0 rotations, the error is 9.0 and calculate returns 1.8. That is 180 percent output. WPILib will not warn you, because from its point of view it did the arithmetic you asked for.

Your clamp is still mandatory, on every closed loop, forever. Nothing about adopting the class moves that responsibility off you.

4 The argument order trap

calculate(measurement, setpoint). Measurement first. Target second.

Both arguments are double, so swapping them compiles without a warning. What it does is flip the sign of the error, which flips the sign of every output, which means the controller drives the mechanism away from the target. And because the mechanism is moving away, the error grows, so the output grows, so it never turns around.

You will run this in the sandbox in section 8. The arm ends up at minus 178 with the motor still pinned at full reverse.

5 Tolerance and atSetpoint

Two calls turn "how far off am I" into a yes or no answer.

Arm.javaJava
pid.setTolerance(0.25);        // rotations. what counts as arrived

double output = pid.calculate(getPosition(), 9.0);

if (pid.atSetpoint()) {        // true when the last calculate saw an error inside 0.25
    // we are there
}
Verify for current season

setTolerance, atSetpoint and reset are not in our curriculum's verified syntax boxes, which only cover the constructor and calculate. They are long-standing parts of the WPILib class and PenguinSim provides them, but check the current WPILib documentation for their exact signatures before you rely on them. The three-argument constructor and calculate(measurement, setpoint) you can treat as verified.

Remember this call, because Unit 7 needs it

atSetpoint() is going to become a command's isFinished(), unchanged, in the very next unit. Every mechanism that has to finish before the next step can begin uses exactly this call. It is the most important method on the page.

One honest caveat. atSetpoint() reports on the most recent calculate() call. Ask it without having called calculate() this cycle and you get a stale answer. It also does not mean the mechanism has stopped. An arm travelling fast can be inside tolerance for one cycle on its way straight past.

6 reset and stale state

A PIDController remembers things between calls. It keeps the accumulated integral and the previous error, because it needs both to compute I and D.

That memory is a problem when you reuse the controller. Suppose you send the arm up, interrupt it halfway, and send it up again ten seconds later. The leftover integral from the first attempt is still sitting in the object, and the first output of the second attempt jumps for no reason you can see in the code.

Arm.javaJava
// Call this once when a move BEGINS, not every cycle.
public void startMove() {
    pid.reset();      // clears the accumulated integral and the previous error
}

The rule is short: reset the controller when a behaviour starts. In Unit 7 "when a behaviour starts" gets a proper name, and it is initialize().

7 Where the controller lives

One PIDController per mechanism, created once, stored in a field.

Never construct one inside a method that runs every cycle
wrongJava
public void moveToward(double setpoint) {
    PIDController pid = new PIDController(0.2, 0.0, 0.0);   // WRONG
    setSpeed(pid.calculate(getPosition(), setpoint));
}

That is a brand new controller fifty times a second, each one with no memory of the one before it. The integral never accumulates, so I does nothing. There is no previous error, so D does nothing. atSetpoint() is answering about a controller that was born this cycle.

Nothing errors. Nothing warns. It compiles, it runs, and a P-only controller works well enough that you may not notice for weeks. Then you add a D term to fix an oscillation and it changes nothing, and you have no idea why.

8 Run it, then break it on purpose

Sim units again

PenguinSim works in degrees, so the sandbox targets 50.0 with a gain of 0.02 and a tolerance of 1.0. PenguinBot's real arm targets 9.0 rotations with a gain of 0.2 and a tolerance of 0.25, which is what every real-robot block on this page shows. The API is identical either way.

output
[sim] SparkMax on CAN ID 3 (kBrushless) is alive.
tick   1   pos   0.00   raw   1.00   out  0.80   atSetpoint false
tick   2   pos   0.19   raw   1.00   out  0.80   atSetpoint false
tick   3   pos   0.55   raw   0.99   out  0.80   atSetpoint false
tick  15   pos  12.62   raw   0.75   out  0.75   atSetpoint false
tick  30   pos  31.49   raw   0.37   out  0.37   atSetpoint false
tick  45   pos  42.91   raw   0.14   out  0.14   atSetpoint false
tick  60   pos  47.90   raw   0.04   out  0.04   atSetpoint false
arrived at tick 68, stopping

Read the raw and out columns together. On tick 1 the controller asks for 1.00 and the clamp cuts it to 0.80. By tick 15 the controller is asking for 0.75, which is under the limit, so the two columns agree from there on. That is the clamp doing its job and then getting out of the way.

Experiment 1 · swap the arguments

Change pid.calculate(position, TARGET) to pid.calculate(TARGET, position). It compiles.

output
tick   1   pos   0.00   raw  -1.00   out -0.80   atSetpoint false
tick  30   pos -34.95   raw  -1.70   out -0.80   atSetpoint false
tick  60   pos -82.67   raw  -2.65   out -0.80   atSetpoint false
tick  90   pos -130.67   raw  -3.61   out -0.80   atSetpoint false
tick 120   pos -178.67   raw  -4.57   out -0.80   atSetpoint false

The arm runs the wrong way and never comes back. Worse, look at the raw column: it is growing. The further the arm gets from the target the harder the controller pushes it away, so there is no point at which this recovers. On a real robot this is a mechanism driving into its hard stop at full power and staying there.

Experiment 2 · use an untuned gain

Set the gain to 0.005. The loop runs all 120 ticks, atSetpoint stays false the whole time, and the "arrived" line never prints. The class does not rescue a bad number. It only does the arithmetic.

Experiment 3 · delete the clamp

Replace output with raw in the call to arm.set(). At this gain the simulator immediately reports being commanded outside the legal range, and the fried-motor warning from Unit 4 fires.

10 Common mistakes

Watch out for these
  • Thinking the controller moves the motor. It returns a number. You still call set(), and you still clamp first.
  • Putting the setpoint first. Measurement first, setpoint second. It compiles either way and only one of them works.
  • Expecting the class to replace tuning. It does the arithmetic. The numbers are still yours and they still describe your mechanism.
  • Constructing a controller every cycle. That throws away exactly the state that makes I, D and atSetpoint() work, and nothing warns you.
  • Reading atSetpoint() as "the mechanism has stopped." It means the last calculate() saw a small error. A fast arm can be inside tolerance while sailing straight through.
  • Getting the constructor order wrong. kP, kI, kD. Putting a gain in the I slot that belonged in the P slot gives you a mechanism that winds up and takes off.
Build it · PenguinBot

The arm goes closed-loop for real

Your Arm has a hand-written controller, a tuned gain, a homing routine and an atSetpoint helper you wrote yourself. Rewrite it to use PIDController.

  1. One controller field with the tuned gain, and setTolerance in the constructor.
  2. moveToward(double setpoint): calculate, clamp, set. Still one cycle.
  3. goToScore() and goToStowed() as wrappers over it.
  4. atSetpoint() delegating to the controller instead of doing the arithmetic yourself.
  5. startMove() calling reset().
  6. Keep the isHomed() guard.
  7. Bonus. Add a follower motor on CAN ID 4 that mirrors the pivot, so the arm has two motors. Notice how much of the controller code has to change.

Working code prints this:

[sim] SparkMax on CAN ID 4 (kBrushless) is alive.
Raising to score:

  tick  60   pos  48.09   atSetpoint false
  arrived at tick 68

  tick  60   pos   1.92   atSetpoint false
  arrived at tick 68

Both moves take 68 cycles, which is what you would expect from a controller that only knows about the size of the error and not about which direction it is going.

Reveal the solution

Real-robot version, with real imports and PenguinBot's numbers in rotations.

Arm.java · solutionJava
import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;
import edu.wpi.first.math.controller.PIDController;

public class Arm {
    private final SparkMax pivot    = new SparkMax(3, MotorType.kBrushless);
    private final SparkMax follower = new SparkMax(4, MotorType.kBrushless);   // bonus

    public  static final double SCORE_POSITION  = 9.0;    // rotations
    public  static final double STOWED_POSITION = 0.0;
    private static final double TOLERANCE       = 0.25;
    private static final double MAX_OUTPUT      = 0.8;    // the team's 80 percent rule

    // One controller, created once. Tuned in the previous lesson.
    private final PIDController pid = new PIDController(0.2, 0.0, 0.0);

    private boolean homed = false;

    public Arm() {
        pid.setTolerance(TOLERANCE);
    }

    public double getPosition() { return pivot.getEncoder().getPosition(); }
    public boolean isHomed()    { return homed; }
    public boolean atSetpoint() { return pid.atSetpoint(); }

    public void home() {
        pivot.getEncoder().setPosition(0.0);
        homed = true;
    }

    public void setSpeed(double speed) {
        double safe = Math.max(-MAX_OUTPUT, Math.min(MAX_OUTPUT, speed));
        pivot.set(safe);
        follower.set(safe);      // bonus: two motors, one method
    }

    public void stop() {
        pivot.set(0);
        follower.set(0);
    }

    // Call once when a move BEGINS. Clears stale integral and previous error.
    public void startMove() {
        pid.reset();
    }

    // Call EVERY 20 ms while the arm should be holding a setpoint.
    public void moveToward(double setpoint) {
        if (!homed) { stop(); return; }
        double output = pid.calculate(getPosition(), setpoint);   // measurement, setpoint
        setSpeed(output);                                          // setSpeed clamps
    }

    public void goToScore()  { moveToward(SCORE_POSITION);  }
    public void goToStowed() { moveToward(STOWED_POSITION); }
}

Put that next to the hand-written version from two lessons ago. Almost nothing changed. That is the point. The class is a small convenience over arithmetic you already understand, which is precisely why you wrote it by hand first.

  • setSpeed still clamps. Adopting the class did not remove the 80 percent rule, and keeping the clamp inside setSpeed means the bonus follower is protected too.
  • The bonus is one line. Nothing outside Arm knows the arm gained a motor, and the controller did not change at all. That is the ownership rule from Unit 3 paying rent.
Look at the shape of what you just wrote
  • startMove(), which runs once at the beginning.
  • moveToward(), which runs every cycle.
  • atSetpoint(), which answers whether you are done.

That is initialize(), execute() and isFinished(). You have now written a Command by hand, twice, without knowing it had a name. Unit 7 gives it one.

Unit 6 is finished and PenguinBot's arm arrives where you tell it. But something has to call moveToward() every 20 milliseconds, and something has to notice when it is finished so the next step can start. Nothing in your code does either yet. That is Unit 7.
