1 Why this matters

The flywheel

A flywheel is a heavy spinning disc. It is hard to get moving and, once moving, it stays moving. You cannot shoot until it is up to speed, say 4000 RPM.

Now try to write that with nothing but "turn the motor on":

  • Turn it on at full power to get there fast, and you fry the motor.
  • Turn it on gently, and now how do you know when to shoot? Something has to wait and decide.
  • Turn it on and immediately run the feeder, and you shoot into a wheel that is not ready.

What is missing is not a motor call. It is a behaviour with an end: run the flywheel until it reaches 4000 RPM, and only then report finished so the next step can begin. That is a Command, and it is the reason command based robots exist.

2 The four layers

This diagram is the backbone of the whole track. Learn it in this exact order.

RobotContainer binds a button press to… ↓ Command a unit of behaviour with a clear END, which tells… ↓ Subsystem the object that owns the hardware, which calls… ↓ Motor and the mechanism finally moves

Two rules follow from the picture, and they are the whole lesson:

  • Information flows down, never sideways. A command never reaches past a subsystem to a motor. RobotContainer never reaches past a command to a subsystem method.
  • Subsystems are the only place motors get touched. No exceptions.

3 Subsystems own hardware

A subsystem is one mechanism. It holds the motor objects for that mechanism, and it exposes methods that describe what the mechanism can do. Nothing outside it ever sees a motor.

IntakeSubsystem.java · shape onlyJava
public class IntakeSubsystem extends SubsystemBase {

    // 1. the hardware this mechanism owns, and nobody else touches
    private final SparkMax roller = new SparkMax(2, MotorType.kBrushless);

    // 2. verbs the rest of the robot is allowed to use
    public void runRoller(double speed) { }
    public void stop() { }

    // 3. periodic() runs every 20 ms, always, command or no command
    @Override
    public void periodic() { }
}

Read the method names. runRoller and stop describe the mechanism, not the motor. That is deliberate. When the mechanical team replaces one motor with two, every caller in the project keeps working, because none of them knew there was one motor to begin with.

4 Commands have an end

A command is one behaviour, and its defining feature is that it can say when it is done. It has four methods, and WPILib runs them on the robot's 20 ms loop.

MethodRunsUsed for
initialize()Once, when the command startsSet up. Start a timer, command a speed
execute()Every 20 ms while the command is activeAdjust something continuously
isFinished()Every cycle, after executeReturn true when the behaviour is complete
end(boolean interrupted)Once, when the command stopsClean up. Stop the motor
Two names people mix up

execute() belongs to a command and only runs while that command is scheduled. periodic() belongs to a subsystem and always runs. They are two different methods on the same 20 ms loop. The onboarding video calls execute() "the periodic," and that is worth un-learning now.

Unit 7 teaches commands properly. What matters today is why isFinished() exists at all: so behaviours can be put in order. "Arm up, then outtake" is impossible unless the first step can say when it is done.

5 RobotContainer wires it up

RobotContainer creates one instance of each subsystem, creates the commands, and connects controller inputs to those commands. It runs once at startup and then mostly sits there. It does not run the robot. It wires it.

The driver presses cross ↓ RobotContainer a binding written once at startup fires ↓ Command the scheduler starts it and calls its methods every 20 ms ↓ Subsystem the command calls runRoller(0.7) ↓ Motor the subsystem tells the roller motor to spin

Three things to notice, because they are the concepts made visible:

  • initialize() ran once, before any cycle. end() ran once, after the last one.
  • The subsystem's periodic() ran on every single cycle, next to the command's execute(). Two different methods, same loop.
  • The command ended because isFinished() returned true. Nothing else stopped it.
Try this in the sandbox
  • Change isFinished() to return false; and run it. The command never ends, the scheduler runs out of cycles, and the sim tells you a real robot would do this forever.
  • Change the time from 0.20 to 1.0 and count the cycles. Fifty cycles per second is not a figure of speech.
  • Move intake.runRoller(0.7) from initialize() into execute(). The behaviour looks identical here, and Unit 7 explains when that difference matters.

The timer is a placeholder end condition. A real intake command would end when a sensor says the game piece is in, and reading a sensor is Unit 5.

7 The ownership rule

Here is why the layers are worth the trouble. Suppose two commands both write directly to the arm motor, each every 20 ms. One wants 0.5 and one wants minus 0.3.

The code compiles. Nothing errors. The bus is fine. The arm judders, because on each cycle whichever command ran last wins, and they alternate fifty times a second.

One subsystem owning the hardware makes this impossible to write by accident. Everything else has to ask, and Unit 7 adds a mechanism that makes the framework refuse to run two commands that need the same subsystem.

subsystem
A noun. One mechanism, owning its hardware, exposing verbs.
command
A verb. One behaviour, with a defined end.
RobotContainer
The wiring. Creates the subsystems and commands and connects inputs to them.
end condition
What isFinished() returns true on. The thing that makes sequencing possible.
scheduler
The part of WPILib that runs every scheduled command's methods once per 20 ms cycle.

9 Common mistakes

Watch out for these
  • Treating commands and subsystems as the same thing. A subsystem is a noun that owns hardware. A command is a verb that has an end. One arm, many things you can ask it to do.
  • Calling the motor from RobotContainer because it is shorter. It works right up until two pieces of code want the arm at once, and then it fails with no error at all.
  • Thinking every behaviour needs a command class. Instantaneous behaviour can bind straight to a subsystem method. The ChairBot never used a single command. Commands earn their place when behaviour takes time and has to finish.
  • Calling execute() the subsystem's periodic. Two different methods on the same loop. periodic() always runs. execute() runs only while its command is scheduled.
  • Thinking RobotContainer runs the robot. It wires the robot. It runs once at startup and then mostly sits there.
Design it · PenguinBot

Design PenguinBot's layers

You have the project map. Next lesson you write your first real motor code, so decide now where each piece of PenguinBot's scoring behaviour belongs.

The behaviour: when the driver presses one button, PenguinBot raises the arm to the scoring position, then spits the game piece out, then lowers the arm back to stowed.

  1. Write the three layers on paper. Class names and method names only, no bodies.
  2. Then answer this. Which of the three steps needs to be a command rather than a direct method call, and why?
  3. And this. What goes wrong if all three steps fire at the same instant?
Reveal the reference design

Subsystems, which own the hardware and expose verbs:

  • IntakeSubsystem with runRoller(double speed), outtake(), stop(). Motor on CAN ID 2.
  • ArmSubsystem with setSpeed(double), getPosition(), goToScore(), stop(). Motor on CAN ID 3.

Commands, which are behaviour with an end:

  • ArmToScoreCommand, which runs until the arm reaches the scoring setpoint.
  • ArmToStowCommand, the same thing back to stowed.
  • ScoreSequence, which runs arm up, then outtake, then arm down, in order.

RobotContainer, which is wiring:

  • One IntakeSubsystem and one ArmSubsystem.
  • driver.cross() starts ScoreSequence.

Which step needs to be a command? Both arm moves. Raising the arm takes time. The motor runs for many 20 ms cycles and has to stop in the right place, so something must decide when it has arrived and report finished. Spitting the piece out is instantaneous, so it is a direct subsystem call. In Unit 8 you wrap that call so it can sit inside a sequence.

If all three fire at once, you outtake into the floor while the arm is still moving. Sequencing is not tidiness. It is the difference between scoring and not.

That is the design. Next lesson you write the bottom layer for real, and make a motor spin.
