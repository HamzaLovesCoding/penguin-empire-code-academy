1 Why this matters

A correction, and it is the reason this lesson exists

Our curriculum's narrator says that init is "what happens when it stops." That is wrong.

Init runs once when the mode starts. Periodic runs every 20 milliseconds while you are in that mode.

Get this backwards and you will put setup code somewhere that runs fifty times a second, or per-cycle logic somewhere that runs once. Both fail quietly, and neither produces an error message that points at the cause.

The one time this team touched this file

Every guide tells you to leave Robot.java alone, including this one. So it is worth knowing what happened the one time the team edited it.

They changed testInit to run a PathPlanner routine, so they could trigger an autonomous path from the Driver Station's test mode without waiting for a real autonomous period.

Notice the shape of that reason. It was not "I needed to add robot logic." It was "I needed a different entry point for testing." That is what this file is for.

2 Four modes, chosen at the Driver Station

Teleoperated, autonomous, test and practice. You pick the mode in the Driver Station, not in code. Your code has a handler for each one. The Driver Station decides which one is live.

Focus on teleop and autonomous. Test and practice are optional and most teams barely use them, which is exactly why testInit is available as a debugging entry point.

3 Every mode has an Init and a Periodic

The symmetry is the whole idea.

MethodRuns
robotInit()Once, when the robot program starts
robotPeriodic()Every 20 ms, in every mode, always
autonomousInit()Once, when autonomous begins
autonomousPeriodic()Every 20 ms while in autonomous
teleopInit()Once, when teleop begins
teleopPeriodic()Every 20 ms while in teleop
testInit() and testPeriodic()The same shape, for test mode
disabledInit() and disabledPeriodic()The same shape, while disabled

There is no method that runs when a mode ends. The closest thing is the next mode's Init, which is exactly why teleopInit() is where you clean up after autonomous.

Disabled is a mode too

While disabled, robotPeriodic() still runs, and therefore the scheduler runs, and therefore every subsystem's periodic() runs. Your telemetry keeps updating on the dashboard while the robot sits disabled on the field. What does not happen is motors moving.

That is genuinely useful between matches, and it explains why the arm's position still shows on your dashboard when nothing can possibly move.

4 The one line that makes it all work

Robot.javaJava
@Override
public void robotPeriodic() {
    CommandScheduler.getInstance().run();
}

You have been calling that method by hand, in a for loop, in every sandbox since Unit 7. Here is who calls it on a real robot.

That single call runs every subsystem's periodic(), polls every button, and executes every scheduled command. It is the entire contents of Units 7 and 8, driven from one line.

Delete it and nothing tells you

Take that line out and the robot compiles, deploys, connects, shows Robot Code green on the Driver Station, and enables. Every button does nothing. No subsystem periodic() runs. No command executes. There is no error anywhere.

You will do this in the sandbox in section 8. It is the most instructive experiment in Unit 8.

It lives in robotPeriodic() rather than in teleopPeriodic() for a specific reason: robotPeriodic() runs in every mode. Put the scheduler call in teleopPeriodic() and autonomous does nothing at all.

5 How autonomous actually starts

  • autonomousInit() asks RobotContainer for the autonomous command, which is the getAutonomousCommand() stub you wrote two lessons ago, and schedules it.
  • autonomousPeriodic() is usually empty, because the scheduler in robotPeriodic() is already running the command.
  • teleopInit() cancels the autonomous command, so a routine still running at the buzzer does not fight the driver.
The cancel is not optional

Nothing cancels an autonomous command for you when the mode changes. Leave that line out and an unfinished routine keeps driving into teleop, competing with the driver for the same subsystems.

It is a confusing failure to diagnose, because the driver's own bindings partly work. Whichever command was scheduled most recently wins, so the robot responds intermittently.

6 The whole file

Robot.javaJava
package frc.robot;

import edu.wpi.first.wpilibj.TimedRobot;
import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.CommandScheduler;

public class Robot extends TimedRobot {

    private Command autonomousCommand;
    private RobotContainer robotContainer;

    @Override
    public void robotInit() {
        robotContainer = new RobotContainer();   // ONCE. builds subsystems and bindings
    }

    @Override
    public void robotPeriodic() {
        CommandScheduler.getInstance().run();    // EVERY 20 ms, EVERY mode. the engine.
    }

    @Override
    public void autonomousInit() {
        autonomousCommand = robotContainer.getAutonomousCommand();
        if (autonomousCommand != null) {
            autonomousCommand.schedule();        // ONCE, at the start of auto
        }
    }

    @Override
    public void autonomousPeriodic() {
        // usually empty. the scheduler above is already running the command
    }

    @Override
    public void teleopInit() {
        if (autonomousCommand != null) {
            autonomousCommand.cancel();          // do not let auto fight the driver
        }
    }

    @Override
    public void teleopPeriodic() {
        // usually empty. bindings and the scheduler do the work
    }
}
Both Periodic methods being empty is a good sign

It looks like something is missing. It is not. Empty teleopPeriodic() and autonomousPeriodic() are the mark of a well-structured command-based robot. The work lives in subsystems and commands, where it belongs, and the scheduler drives it.

Verify for current season

This whole file comes from the project template, and templates change. The base class, the exact method names, the generated autonomous pattern and which methods are scaffolded have all moved between versions. Read the Robot.java your own project generated rather than copying this one.

The init versus periodic correction in section 1 is not season-dependent. It is the one thing on this page that will still be true in ten years.

  • The arm moved only while the autonomous command was scheduled.
  • At the teleop transition the command was cancelled and the arm stopped being driven, ending at 42.98 instead of its 50.0 setpoint. It drifted from 37.76 to 42.98 after the cancel because a stopped motor coasts, which you met in Unit 7. Nothing was pushing it.

Three experiments, and the first one is the point of the lesson

  • Delete CommandScheduler.getInstance().run() from robotPeriodic(). The arm never moves, in any mode. Every Init still prints, so the program is clearly running. Nothing errors. That one line was the entire framework.
  • Remove the cancel() from teleopInit(). The autonomous command carries on driving the arm all the way to 50.0, into teleop, while the driver is trying to drive.
  • Move the scheduler call from robotPeriodic() into teleopPeriodic(). Autonomous does nothing at all, and the arm only starts moving at tick 40.

10 Common mistakes

Watch out for these
  • Thinking Init runs when the mode ends. Init runs once at the start. This is the narrator's error and the reason this lesson exists.
  • Writing driving code in teleopPeriodic(). In a command-based robot it is usually empty. Your bindings and commands do the work.
  • Assuming robotPeriodic() only runs when enabled. Every mode, including disabled.
  • Putting autonomous logic in autonomousPeriodic(). autonomousInit() schedules a command and the scheduler runs it.
  • Treating empty Periodic methods as something forgotten. They mean your structure is right.
  • Believing you should never touch this file. Almost never. The real exception is an entry point for testing.

Reveal the solution

1. It is in robotPeriodic(). That matters because robotPeriodic() runs in every mode and while disabled, so subsystem periodic() methods, button polling and command execution all keep working regardless of mode. If it were in teleopPeriodic(), autonomous would do nothing at all.

2. Power-on to a button press

  1. robotInit() runs once. It constructs RobotContainer, which constructs ArmSubsystem and IntakeSubsystem, each registering itself with the scheduler, and calls configureBindings().
  2. disabledInit() runs once. robotPeriodic() starts running every 20 milliseconds, so subsystem periodic() methods run and telemetry updates even though nothing can move.
  3. The Driver Station is set to Teleoperated and Enabled. teleopInit() runs once and cancels any autonomous command.
  4. Every 20 milliseconds robotPeriodic() calls the scheduler, which runs subsystem periodic() methods and polls the buttons.
  5. The driver presses cross. The rising edge schedules ScoreSequence, whose initialize() runs immediately.
  6. On each following tick the scheduler executes the sequence's current command, and ArmToScoreCommand.execute() calls arm.goToScore(), which runs one controller cycle and calls pivot.set(...).
  7. The roboRIO puts a message on CAN, the SparkMax on ID 3 receives it, the Neo turns, and the arm rises.

3.

Robot.javaJava
@Override
public void testInit() {
    // Legitimate edit: an entry point for testing, not robot logic.
    // Lets us run a full scoring cycle from the Driver Station with no
    // driver and without waiting for a real autonomous period.
    CommandScheduler.getInstance().schedule(
        new ScoreSequence(robotContainer.arm, robotContainer.intake));
}

This is legitimate because it adds no behaviour. Every command it runs already exists and is defined elsewhere. Robot.java is only being used as a trigger, which is the same reason this team once edited testInit to fire a PathPlanner routine.

4. The common temptation is "make the arm hold its position whenever the robot is enabled," and putting that in teleopPeriodic(). It belongs in ArmSubsystem, either as a default command or as behaviour inside the subsystem. Robot.java decides when modes start. It does not decide what mechanisms do.

Bonus. If robotInit() does not create the RobotContainer, no subsystems are ever constructed, so nothing registers with the scheduler, no bindings are configured, and no periodic() runs. The robot boots, connects, shows Robot Code green, and enables. Every button does nothing. It is exactly the same silent failure as deleting the scheduler line, arriving from the other direction.
