1 Why this matters

Two days, and the answer took fifteen seconds

The team once lost two full days to a motor that had stopped running. The cause turned out to be a commanded value set far too high. The two days went into not knowing where to look. Was it the code? The wiring? The mechanism?

The REV Hardware Client answers that question in about fifteen seconds. Plug a USB-C cable into the SparkMax and run the motor from the client's Run tab. If it spins, the wiring and the motor are fine and the problem is in your code. If it does not spin, stop reading your code, because the code was never involved.

This is the most valuable habit in Unit 2. Cut the system in half and find out which half is broken.

2 Two clients, two vendors

Each vendor ships a desktop application for its own hardware. They are not interchangeable, and they do not even connect the same way.

ClientTalks toConnects byDoes
REV Hardware ClientSparkMax, SPARK Flex, Neos, the PDHUSB-C, straight to the deviceSet CAN IDs, update firmware, change parameters, run the motor, read faults
Phoenix TunerKrakens and other CTRE devicesOver the robot's radioList and name devices, set IDs, update firmware, run and tune

The USB-C detail matters more than it sounds. A SparkMax can be tested on a workbench with no roboRIO, no radio, and no robot at all. A Kraken has to be on a powered robot you can reach over the network.

Verify for current season

Vendor tools get renamed and replaced. REV notes that teams on REVLib 2026 or newer need REV Hardware Client 2, and CTRE's tool has been through several versions. Download the version that matches the library your project pulls in.

3 Inside the REV Hardware Client

Plug a SparkMax into your laptop over USB-C and the client finds it automatically. Selecting the device reveals four tabs worth knowing.

Basic
The common settings. Device Identify blinks the controller's LED so you can tell which physical device you are looking at. This is also where you set the CAN ID. REV's documentation is blunt: any configured SPARK MAX must have a CAN ID.
Advanced
Every configurable parameter, without writing code. Useful for one-off testing, dangerous as a permanent solution, because settings that live only on a device are invisible to whoever reads your repository.
Run
Drives the motor over USB with no control system at all. This is the isolation test from the story above. It also does live PID tuning, which you will use in Unit 6.
Update
Shows the firmware version on the device and updates it. Out of date firmware causes failures that look exactly like code bugs.
Save before you unplug

Changes you make in the client are not permanent until you persist them to the controller's memory. In older versions of the client that button was labelled Burn Flash. As of client version 1.7.0 it is called Persist Parameters. Same operation, different name, and forgetting it means your CAN ID quietly reverts the next time the robot is power cycled.

4 Sticky faults

A sticky fault is a record that something went wrong at some point. It does not mean something is wrong now. The device latches the fault so you can find out about a problem that happened during a match, while you were looking at the field instead of a screen.

The right procedure is:

  1. Read the fault. It tells you what category of problem occurred.
  2. Fix the actual cause.
  3. Clear the fault.
  4. Run the mechanism again.

Step four is the one people skip. If the fault comes straight back, the problem is live and you have not fixed it. If it stays clear, you have. Clearing faults without fixing anything just deletes your only evidence.

5 Isolation, as a procedure

When a mechanism does not move, there are exactly three places the problem can be.

CODE WIRING BUILD your program power, CAN, the mechanism sent the wrong connectors, itself: jammed, value, or none a dead motor seized, unbolted

Each check below rules out a whole category, and they are ordered cheapest first.

Reading code comes last because it is the only step that cannot rule anything out by itself. You can stare at correct code for two days.

7 Common mistakes

Watch out for these
  • Reading a sticky fault as a live problem. It means something was wrong at some point. Clear it after you fix the cause, and if it returns it is live.
  • Thinking CAN IDs are set in code. Your code says which ID it wants. The vendor client is where the device is told its ID. Mismatch them and nothing moves and nothing complains at compile time.
  • Assuming a dead motor means bad code. Prove it. Run the motor from the client and find out in fifteen seconds whether code is even involved.
  • Treating the two clients as interchangeable. Each talks only to its own vendor's hardware, over a different connection.
  • Leaving firmware to somebody else. Programmers push firmware. It sits on your list right next to imaging the roboRIO.
  • Configuring a device only in the client. Settings that live on a device and not in your repository are invisible to the next person, and they vanish if the controller is replaced.
Build it · PenguinBot

PenguinBot's device sheet

PenguinBot's project has REVLib installed. Before any code can address a motor, every device needs a known and recorded identity, and you need to know which tool assigns it.

  1. Build the sheet. One row per device: name, hardware, CAN ID, which client sets that ID, and how it connects.
  2. Add an alive test to each row. One line describing what you would do in that client to prove the device is working.
  3. Write two rules at the bottom that you would want a tired teammate to read at 11pm.
