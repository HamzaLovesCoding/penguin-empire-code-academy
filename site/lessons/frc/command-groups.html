1 Why this matters

Scoring is four things in a specific order

PenguinBot can raise its arm to a setpoint and stop there. It can spin its intake. Scoring is those two capabilities used in order.

a scoring cycle
arm up  ->  spit the piece out  ->  wait for it to clear  ->  arm back down

Try that with four button bindings and the driver has to time it by hand, mid-match, while somebody is defending them.

Try it with four method calls in a row and all four happen within the same 20 milliseconds. The intake fires while the arm is still at the bottom and the piece lands on the floor.

Order needs duration, and duration needs an end condition. That is what commands have been for all along.

2 The verified syntax

Verified syntax · WPILib

// Run in order, each waiting for the previous to finish:
new SequentialCommandGroup(cmd1, cmd2, cmd3);

// Run all at the same time:
new ParallelCommandGroup(cmdA, cmdB);

Modern WPILib also offers factory methods that build the same groups with less typing. Check what your season provides and follow whatever your team's existing code already uses, since mixing both styles in one project is worse than either. The class form above is verified in our curriculum and works everywhere.

PenguinSim does not ship these classes, so the sandbox builds small versions by hand. That turns out to be useful, because it makes section 4 something you can read rather than something you take on trust.

3 A group is a command

This is what lets you build bigger routines out of groups. SequentialCommandGroup extends Command. It has initialize(), execute(), isFinished() and end(), just like everything you wrote in Unit 7.

So a group can be bound to a button, nested inside another group, or used as an entire autonomous routine. There is no separate category of thing here.

That has a consequence worth stating now: your whole autonomous routine in Unit 11 will be one sequential group made of commands you have already written.

4 How a sequence actually runs

People imagine something clever is happening. It is not.

a sequential group, in fullJava
initialize()  -> initialize the FIRST command
execute()     -> execute the current command
                 if it isFinished(): end it, and initialize the NEXT one
isFinished()  -> true when the last command has finished

Two consequences follow directly, and the sandbox shows both.

  • The group finishes when its last command finishes. Give it a command that never ends and the whole group never ends, along with any autonomous routine containing it.
  • An InstantCommand inside a sequence acts the moment the previous step finishes, because it does its work in initialize() and the group calls that immediately.

5 Parallel, and what it costs

Parallel is for things that genuinely can happen at once. Raising the arm while driving to the scoring position uses two different subsystems, so it is safe and it halves the time.

A parallel group ends when all its members end. One slow member sets the pace, and one member that never ends means the group never ends.

Two commands needing the same subsystem cannot be parallel

This is a hard constraint, not a style preference. Putting an arm-up command and an arm-down command in the same parallel group means two commands driving one mechanism toward opposite setpoints, which is precisely what requirements exist to prevent.

Parallel is not a way to make things faster in general. It is a way to overlap work on different mechanisms. Two arm commands in parallel is not faster. It is broken.

6 WaitCommand

new WaitCommand(0.5) does nothing for half a second and then finishes. It looks trivial and it is essential, because physical things take time that no sensor is measuring. The game piece needs a moment to clear the roller before the arm comes down.

A wait is a guess

Be honest about what a WaitCommand is. It is a bet that the robot will behave the same way twice. Where a sensor can tell you the piece has cleared, use the sensor. Waits are what you reach for when you have no sensor, and every one of them is a place your routine can go wrong on a cold battery or a sticky roller.

It also does not block the robot. It pauses its own sequence. Every subsystem's periodic(), every other command and the whole scheduler carry on at full speed.

7 Designing the scoring sequence

Walk the decision step by step. The reasoning is the transferable part.

StepWhere it goesWhy
Arm to scoreFirst, aloneThe piece must be up before it is released
Outtake onImmediately afterInstantaneous, so an InstantCommand
WaitAfterGive the piece time to clear the roller
Outtake offAfterInstantaneous again
Arm to stowedLastOnly safe once the piece is gone

Now the counter-example, because it is what makes the reasoning stick. Could steps one and two be parallel? No. You would spit the piece out at floor level. Could the arm stow while the intake stops? Yes, and that is a real optimisation, which the exercise builds as a nested parallel group.

ScoreSequence.javaJava
import edu.wpi.first.wpilibj2.command.SequentialCommandGroup;
import edu.wpi.first.wpilibj2.command.InstantCommand;
import edu.wpi.first.wpilibj2.command.WaitCommand;
import static frc.robot.Constants.IntakeConstants;

public class ScoreSequence extends SequentialCommandGroup {

    public ScoreSequence(ArmSubsystem arm, IntakeSubsystem intake) {
        addCommands(
            new ArmToScoreCommand(arm),                        // takes time
            new InstantCommand(() -> intake.runRoller(IntakeConstants.kOuttakeSpeed)),
            new WaitCommand(0.5),                              // let the piece clear
            new InstantCommand(intake::stop),
            new ArmToStowCommand(arm)                          // takes time
        );
    }
}

intake::stop is a method reference, which is the same idea as the lambda written shorter. And because the group is itself a command, binding it is one line.

RobotContainer.javaJava
driver.cross().onTrue(new ScoreSequence(arm, intake));

Notice what just happened. The binding got simpler while the behaviour got more sophisticated.

Read it against the design table.

  • Steps happened strictly in order. Nothing from step three occurred before step two was done.
  • The roller was negative only between outtake on and outtake off.
  • The arm stayed at the top through the whole wait. It drifted from 49.07 to 49.71 because a stopped motor coasts, which you met in Unit 7. No step was driving it.
  • The arm came back down only after the outtake stopped.
  • The group reported finished after its last command, at tick 163.

Three experiments, and one of them is the important one

  • Change the wait to 0.1 and then 2.0. The whole sequence's length changes and nothing else does. Think about what the game piece is doing during that time.
  • Reorder the steps so the outtake InstantCommand comes first. The piece is released at floor level. This is the most instructive mistake in the lesson, so make it deliberately.
  • Give the first ArmToCommand a setpoint the mechanism cannot reach, such as 500.0. Read the next callout first.
One stuck step freezes everything after it

With an unreachable setpoint on step one, the arm drives at full output forever and steps two through five never happen. The intake never runs. The arm never comes down. The sequence never reports finished.

No error. No warning. The robot looks like it is working, because the arm really is moving.

In Unit 11 that is a whole autonomous routine doing nothing for the entire autonomous period while the crowd watches. The defence is the timeout you wrote in Unit 7, and the exercise puts it back.

10 Common mistakes

Watch out for these
  • Thinking a group is a special kind of thing. A group is a command. Bind it, nest it, or use it as an autonomous routine.
  • Using parallel wherever possible because it is faster. Only where the commands need different subsystems and doing them together is physically safe.
  • Expecting a parallel group to end when the first member ends. It ends when all of them do.
  • Thinking WaitCommand blocks the robot. It pauses its own sequence. Everything else carries on.
  • Assuming a stuck step will time out. Nothing times out on its own. Give commands that could hang their own timeout.
  • Replacing small commands with one big one. Composition is the opposite move. Keep small commands that do one thing, and those same commands become your autonomous routine.
Build it · PenguinBot

Score from one button

RobotContainer binds four buttons to four separate behaviours, and the driver has to sequence a scoring cycle by hand. Take that job away from them.

  1. Write ArmToStowCommand, the same shape as ArmToScoreCommand but targeting the stowed setpoint from Constants.
  2. Write ScoreSequence: arm up, outtake on, wait, outtake off, arm down.
  3. Rebind cross() to the sequence, replacing the bare arm command.
  4. Write one sentence per step explaining why it cannot move earlier in the order.
  5. Bonus 1. Make the last two steps a nested ParallelCommandGroup so the intake stops while the arm stows, and say how much time that saves.
  6. Bonus 2. Add the timeout from Unit 7 back onto ArmToScoreCommand so a jammed arm cannot freeze the whole sequence.
Reveal the solution
commands/ArmToStowCommand.javaJava
import edu.wpi.first.wpilibj2.command.Command;

public class ArmToStowCommand extends Command {
    private final ArmSubsystem arm;

    public ArmToStowCommand(ArmSubsystem arm) {
        this.arm = arm;
        addRequirements(arm);
    }

    @Override public void initialize()    { arm.startMove(); }
    @Override public void execute()       { arm.goToStowed(); }
    @Override public boolean isFinished() { return arm.atSetpoint(); }
    @Override public void end(boolean interrupted) { arm.stop(); }
}
commands/ScoreSequence.javaJava
import edu.wpi.first.wpilibj2.command.SequentialCommandGroup;
import edu.wpi.first.wpilibj2.command.ParallelCommandGroup;
import edu.wpi.first.wpilibj2.command.InstantCommand;
import edu.wpi.first.wpilibj2.command.WaitCommand;
import static frc.robot.Constants.IntakeConstants;

public class ScoreSequence extends SequentialCommandGroup {

    public ScoreSequence(ArmSubsystem arm, IntakeSubsystem intake) {
        addCommands(
            // 1. Raise first. Releasing at floor level drops the piece on the floor.
            new ArmToScoreCommand(arm),

            // 2. Now release. Instant, because there is nothing to wait for.
            new InstantCommand(() -> intake.runRoller(IntakeConstants.kOuttakeSpeed)),

            // 3. Give the piece time to physically clear the roller. No sensor for
            //    this, so it is a timed guess. Keep it as short as reliably works.
            new WaitCommand(0.5),

            // 4 and 5 together. The intake can stop WHILE the arm comes down:
            //    different subsystems, no conflict.
            new ParallelCommandGroup(
                new InstantCommand(intake::stop),
                new ArmToStowCommand(arm)
            )
        );
    }
}

Why each step cannot move earlier

  1. Arm up. Everything after it assumes the piece is at scoring height.
  2. Outtake on. Before the arm is up, this releases the piece onto the floor.
  3. Wait. Stopping the roller immediately would trap the piece half out.
  4. Outtake off. Before the wait, the piece has not cleared.
  5. Arm down. Before the piece is clear, the arm carries it back down with it.

What bonus 1 saves. Roughly one scheduler cycle, which is 20 milliseconds. That is almost nothing, and the pattern is the point. In Unit 11 you will run a whole drivetrain path in parallel with an arm movement, and there the same reasoning saves seconds.

Why bonus 2 matters more than it looks. Without the timeout, a jammed arm means the sequence never gets past step one. During a match. For the whole match. Silently.

One button now runs five commands in the right order. Something still has to call the scheduler every 20 milliseconds, and something has to decide whether you are in teleop or autonomous. That is Robot.java, the file you mostly leave alone, explained.
