1 Why this matters

Hunting down every hard-coded zero

The generated project template writes OperatorConstants.kDriverControllerPort where a beginner would type 0. Our curriculum explains why in one sentence, and it is the least glamorous and most repeatedly true argument in software.

If several files use that port and you later need to change it, you have to find and edit every 0 by hand. With a constant you change it once.

Now make that concrete. Here are the numbers currently sitting in your own PenguinBot code.

numbers you have written so far
new SparkMax(2, ...)             the intake's CAN ID
new SparkMax(3, ...)             the arm's CAN ID
new PIDController(0.2, 0, 0)     the tuned gain, and two zeros that are not the port
moveToward(9.0)                  the scoring setpoint
Math.min(0.8, ...)               the team's power limit
new CommandPS5Controller(0)      the controller port

Two of those zeros mean completely different things and one of them is a controller port. It is nine in the morning on a Saturday, between matches, with the drive team waiting. That is when you find out whether you did this.

2 What belongs there

A constant here is nothing more than a public static final value stored in one file. There is no new language feature in this lesson. The idea is organisational, not technical.

Our curriculum states the textbook rule as a value used in multiple places that rarely changes. Here is the practical version.

Put it in ConstantsLeave it inline
CAN IDs and controller portsA loop bound like i < 4
Speeds, setpoints, tolerancesAn obvious 0 meaning stop
PID gainsSomething used exactly once whose meaning is already clear
Physical dimensions and gear ratios
Anything you will change while tuning
The one test that settles it

Would you ever change this value while standing next to the robot? If yes, it goes in Constants.

3 The pattern

One outer class, one nested static class per mechanism, and a k on the front of every name.

Constants.javaJava
public final class Constants {

    private Constants() { }        // never instantiated. it is all static

    public static final class OperatorConstants {
        public static final int kDriverControllerPort = 0;
    }

    public static final class IntakeConstants {
        public static final int    kRollerCanId  = 2;
        public static final double kIntakeSpeed  = 0.7;
        public static final double kOuttakeSpeed = -0.5;
    }

    public static final class ArmConstants {
        public static final int    kPivotCanId    = 3;
        public static final int    kFollowerCanId = 4;

        public static final double kP = 0.2;      // tuned in Unit 6
        public static final double kI = 0.0;
        public static final double kD = 0.0;

        public static final double kStowedRotations = 0.0;
        public static final double kScoreRotations  = 9.0;
        public static final double kToleranceRot    = 0.25;
        public static final double kHomingSpeed     = -0.15;
        public static final double kSafetyLimitRot  = 12.0;
    }

    public static final class RobotConstants {
        public static final double kMaxOutput = 0.8;   // the team's 80 percent rule
    }
}

Four decisions in that file are worth stating out loud.

  • The k prefix is a WPILib convention, not a rule. The reason to follow it is that when you read kIntakeSpeed in the middle of a method you know instantly it is a configured value and not a local variable. The generated template uses it and your teammates will expect it.
  • Nested static classes, one per mechanism. You get autocomplete that lists everything the arm has the moment you type Constants.ArmConstants., and names can repeat across mechanisms without colliding.
  • Everything is static, so Constants.ArmConstants.kP works with no new anywhere, for the same reason Math.PI does. Your subsystems are instances because there is one real arm. Your constants are static because there is one set of numbers.
  • kMaxOutput lives in RobotConstants, not ArmConstants, because the 80 percent rule is a team rule that applies to every mechanism. Where a constant lives is a design decision, not filing.
Verify for current season

The generated Command Robot template creates Constants.java with an OperatorConstants nested class. Check what your season's template actually scaffolds and follow it, since matching the template is most of the value of following a convention at all.

4 Before and after

ArmSubsystem.javaJava
// BEFORE
private final SparkMax pivot = new SparkMax(3, MotorType.kBrushless);
private final PIDController pid = new PIDController(0.2, 0.0, 0.0);
public void goToScore() { moveToward(9.0); }

// AFTER
private final SparkMax pivot =
    new SparkMax(ArmConstants.kPivotCanId, MotorType.kBrushless);
private final PIDController pid =
    new PIDController(ArmConstants.kP, ArmConstants.kI, ArmConstants.kD);
public void goToScore() { moveToward(ArmConstants.kScoreRotations); }

Be honest about the cost. The second version is longer and takes more typing. What you bought is that every number now has a name, and every one of them lives in a single file you can open on a phone in the pits.

The headline

ArmSubsystem is byte for byte identical in all three runs. The arm stopped somewhere else, and then moved at half power robot-wide, and the class that drives it was never opened.

Run 3 is worth a second look. Halving the output limit did not just make the arm slower. It kept the clamp active for twice as long, so atSetpoint was still false at tick 80 where the default run had already arrived at tick 67. One number in one place changed the timing of the whole mechanism.

6 Where this does not help

Three honest limits, so you do not apply this everywhere out of habit.

  • A value used in exactly one place, with an obvious meaning, is fine inline. Moving it adds a hop for the reader and buys nothing.
  • A constant does not make a number correct. kScoreRotations = 9.0 is still wrong if the arm actually scores at 11.
  • It does not replace the vendor client. Writing kIntakeCanId = 2 while the physical SparkMax is still set to ID 5 is the same silent failure from Unit 2. Your code only ever requests an ID. The device is told its ID in the REV client.

8 Common mistakes

Watch out for these
  • Treating this as tidiness. It is the difference between a one line change and a search across four files while a match is being called.
  • Making every number a constant. A number used once with an obvious meaning is clearer inline.
  • Believing a constant makes the value correct. It makes it easy to change. Nothing more.
  • Trying to instantiate Constants. It is all static, which is why the class has a private constructor.
  • Assuming the constant reaches the hardware. Your code requests an ID. The device is told its ID in the vendor client.
  • Flat naming with no nesting. Then kP can only mean one mechanism, and you end up with kArmP and kDriveP, which is the nesting you avoided, spelled worse.

subsystems/ArmSubsystem.java · afterJava
import static frc.robot.Constants.ArmConstants;
import static frc.robot.Constants.RobotConstants;

public class ArmSubsystem extends SubsystemBase {

    private final SparkMax pivot =
        new SparkMax(ArmConstants.kPivotCanId, MotorType.kBrushless);
    private final SparkMax follower =
        new SparkMax(ArmConstants.kFollowerCanId, MotorType.kBrushless);

    private final PIDController pid =
        new PIDController(ArmConstants.kP, ArmConstants.kI, ArmConstants.kD);

    public ArmSubsystem() {
        pid.setTolerance(ArmConstants.kToleranceRot);
    }

    public void setSpeed(double speed) {
        double max  = RobotConstants.kMaxOutput;
        double safe = Math.max(-max, Math.min(max, speed));
        pivot.set(safe);
        follower.set(safe);
    }

    public void goToScore()  { moveToward(ArmConstants.kScoreRotations);  }
    public void goToStowed() { moveToward(ArmConstants.kStowedRotations); }
    // the rest is unchanged
}

The gearbox change is one line.

Constants.javaJava
public static final double kScoreRotations = 14.0;

Nothing in ArmSubsystem, ArmToScoreCommand or RobotContainer is touched.

Two details in the solution are worth more than the rest.

  • private Constants() { } says in code what the class is for. Nobody should ever write new Constants(), so make that impossible rather than hoping.
  • DriveConstants.kP sitting next to ArmConstants.kP is the clearest justification for nesting there is. Two mechanisms, two gains, the same correct name, no collision, and no need to invent kArmP.
