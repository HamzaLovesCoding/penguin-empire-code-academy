1 Why this matters

Macs cannot run the Driver Station

Team 2551 runs Macs, a PC, and one dedicated Windows laptop. You can write robot code on any of them. You can only enable the robot on the Windows one, because FRC Game Tools has a Windows build and nothing else. WPILib's own requirements page lists Windows 10 or higher, with no macOS or Linux option.

That single fact reorganises how the team works. There is one laptop that goes to the field, and everyone's code eventually has to reach it. A good part of game day in Unit 12 is logistics that follow from this one line.

2 What Game Tools is

FRC Game Tools is one installer from National Instruments containing three things you need:

  • The FRC Driver Station, the application that enables the robot.
  • The roboRIO Imaging Tool and its images, which is how you flash the roboRIO at the start of a season.
  • A LabVIEW update and the runtime components those two tools need.

Keep this separation clear, because new members mix it up constantly:

InstallWhat it is forRuns on
WPILibWriting code and deploying it to the robotWindows, macOS, Linux
FRC Game ToolsEnabling the robot, watching the console, imaging the roboRIOWindows only
Verify for current season

Game Tools is versioned by season and you reinstall it every year. The download location, the installer name, and the exact bundle contents change. Follow the current season's WPILib "Zero to Robot" instructions rather than an old link from a teammate.

3 The Driver Station

The Driver Station is the bar that sits at the bottom of the screen on the driver station laptop. It does not drive the robot. It decides whether the robot may run at all, and it tells you what is wrong.

The most important rule on this page:

Disabled means no code runs

Disabled is not a motor cutout. It stops your program from acting on anything. A robot with three green lights, deployed code, and a controller plugged in still does absolutely nothing until somebody presses Enable. This is the answer to "why isn't my code doing anything" more often than any real bug.

4 The three status indicators

The Driver Station shows three lights. WPILib describes them precisely, and each one points at a different part of the system.

IndicatorGreen meansRed meansWhere to look
CommunicationsThe Driver Station can reach the robotA network problemRadio still booting, Ethernet, radio configuration
Robot CodeYour program is on the roboRIO and runningNot deployed, or it crashedDeploy again, then read the console for an exception
JoysticksAt least one controller is connected and recognisedNo controller in a portPlug it in and assign it to port 0

Read them top down. If Communications is red, nothing below it means anything, because the Driver Station cannot see the robot to know whether the code is running. Fix in that order every time.

5 Modes and Enable

The Driver Station picks which mode the robot is in. Your code does not choose. You write a handler for each mode and the Driver Station decides which one is live.

Teleoperated
The driving portion of a match. Your teleop code runs and the controllers are live.
Autonomous
The opening seconds, with no driver. Your autonomous routine runs.
Practice
Cycles automatically through the match transitions so you can rehearse a full match.
Test
For testing code that does not run in a real match. Unit 8 shows the one case where the team edits this.

Two keyboard shortcuts are worth memorising now, because you will want them under pressure. WPILib documents Enter as disable and Space as emergency stop. Space is the one you hit when a mechanism is about to hurt itself.

6 Where println output goes

In Phase 1 your System.out.println output appeared in a terminal on your own machine. Robot code runs on the roboRIO, not on your laptop, so the output has to travel back over the network.

It arrives in two places:

  • The Driver Station's Messages tab, which WPILib describes as showing "diagnostic messages from the DS, WPILib, User Code, and/or the roboRIO."
  • The RioLog inside VS Code, which opens automatically after a successful deploy.

Until Unit 2's dashboards lesson, printing is your entire debugging toolkit. It is a good one. A line like this is often faster than any dashboard:

ArmSubsystem.javaJava
// this shows up in the Driver Station console, once every 20 ms
System.out.println("arm position: " + armMotor.getEncoder().getPosition());
Printing every loop is noisy

That line runs about fifty times a second and floods the console. It is fine while you are actively watching one number. Take it out afterwards, or you will lose real error messages in the scroll.

7 Triage practice

Here is a mock Driver Station running real situations. Read the lights, the robot state, and the console, then say where the problem is. This is the skill the lesson is actually for.

You just deployed. The robot will not respond to anything.
You powered the robot on twenty seconds ago and opened the Driver Station.
Everything looks healthy. You press the intake button and nothing happens.
The robot is enabled. Autonomous commands work but no button does anything.
The robot drives, but the back left swerve module does nothing and the console keeps printing.

9 Common mistakes

Watch out for these
  • Reading green Communications as "my code is running." Communications only means the Driver Station can reach the robot. Robot Code is the separate light that says your program is loaded and running.
  • Expecting println in the VS Code terminal. Your code runs on the roboRIO. Output travels back to the Driver Station console and to the RioLog.
  • Thinking Game Tools and WPILib are one install. Two installs, two jobs. WPILib to write and deploy, Game Tools to enable and observe.
  • Trying to pick the mode in code. You write a handler per mode. The Driver Station decides which is active.
  • Thinking Disabled just stops the motors. It stops your program from doing anything at all.
Build it · PenguinBot

PenguinBot's bring-up checklist

You can trace a signal and name the hardware. Nothing you write reaches PenguinBot until you can bring the robot up. Write the ordered checklist you would follow, from "the robot is on the cart, powered off" to "the intake spins when I press the button." Every step names what you would look at to confirm it worked.

Keep it. This becomes the seed of the real pre-match checklist in Unit 12.

Reveal the reference checklist

  1. Power on the robot. Look at the roboRIO's lights coming up.
  2. Wait one to two minutes for the radio. There is nothing to look at. This is the step people skip.
  3. Open the Driver Station on the Windows laptop.
  4. Communications green? If not, wait longer, then check the radio and try an Ethernet tether.
  5. Robot Code green? If not, deploy from VS Code and read the console for an exception.
  6. Plug in the controller. Joysticks green? If not, assign it to port 0 in the Driver Station.
  7. Choose Teleoperated in the mode selector.
  8. Press Enable. Nothing before this point can move a motor.
  9. Press the button. If nothing happens now, it is finally time to suspect your code, and the console is where you look first.
