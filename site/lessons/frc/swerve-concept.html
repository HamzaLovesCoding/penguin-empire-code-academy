Unit 9

Field-Centric Swerve

Every new driver arrives with an instinct from video games, and swerve does not work that way. Understanding the difference before you touch a robot is the difference between driving and crashing.

1 Why this matters

Swerve is not a video game

In a game you push the stick forward and the vehicle goes the way it is pointing. Turn, and forward becomes a new direction. That instinct is wrong here, and our curriculum is emphatic about it.

Swerve is field-centric. Push the left stick forward and the robot moves toward the far side of the field, regardless of which way the robot is facing. Spin the robot 180 degrees with the right stick and push forward again. It still goes toward the far side of the field. The robot's body rotated. Its sense of forward did not.

Once that clicks it feels obvious, because it matches how a driver actually sees the field. They are standing behind glass looking at what is effectively a map. The stick points at where they want the robot to be on that map, and the robot's orientation never enters into it.

Until it clicks, drivers crash.

2 What a swerve module is

Each corner of the robot has a module. One motor drives the wheel, and a second motor steers it. Four modules means eight motors, plus an encoder per module so the code knows which way each wheel is currently pointing.

one swerve module, from the side [ steer motor ] turns the whole assembly | to any angle ______|______ | | | drive motor | spins the wheel |_____________| ( ) the wheel
Unit 5 was building to this

A swerve wheel can be pointing in any direction when the robot powers on, and there is no hard stop to home against, because the module can spin freely forever.

That is exactly the decision rule from Relative vs. Absolute Encoders, so swerve steering uses absolute encoders. If you wondered when that lesson would pay off, this is when.

3 What swerve buys you

A tank drivetrain can only drive forward and turn.

A swerve can translate in any direction while simultaneously rotating. It can strafe sideways while spinning to face the goal. It can approach a scoring position from any angle without a three point turn. It can drive across the field in a straight line while keeping its intake pointed at a game piece the entire way.

That last one is the point. Translation and rotation are independent, and that independence is what makes eight motors and a pile of trigonometry worth the trouble.

The phrasing from our curriculum is worth memorising: whatever direction you push on the stick is the direction the robot translates on the field. Think of a top-down map.

The right stick rotates the robot left and right without changing its translation direction. Those are two separate channels of control that never interfere with each other.

In all three of these the driver does exactly one thing: pushes the left stick straight up. What changes is the robot's heading and which mode is on.

The robot slides north. It is still facing west the whole time. If you understand that one sentence you understand field-centric control.

NORTH ^ | stick: up | robot heading: west | result: drives WEST | <---<--[o] robot | travels west "up" now means "the way the nose points", | so the robot drives along its own axis. | +------------------------> EAST

Same driver input. Same robot heading. Two completely different results, and the only difference is which frame of reference the code is using.

For a mix of translation and rotation, each of the four wheels ends up at a slightly different angle and a slightly different speed. Working out those eight numbers, fifty times a second, is what swerve kinematics does.

6 The gyro, and how it goes wrong

The maths in diagram B only works if the robot knows which way it is facing. A gyro measures that heading. Here is the mental model for a single stick push.

Driver pushes the left stick up-and-right (north-east on the field map). The robot is currently facing WEST. -> the code subtracts the robot's heading from the stick's field direction -> it works out that "north-east on the field" is "back-and-right" for THIS robot -> each of the 4 modules is told an angle and a speed -> all four wheels rotate to point north-east, and drive The robot slides north-east. It is still facing west the whole time.

Everything in that trace depends on the heading being correct, which has two entirely practical consequences.

Zero the gyro facing a known direction

The gyro has to be zeroed with the robot pointing somewhere you have agreed on, normally at the start of a match. Zero it while the robot is facing sideways and every subsequent stick input is rotated by 90 degrees.

This is the same class of bug as an unhomed relative encoder from Unit 5. The sensor is reporting perfectly. What is wrong is what zero means.

What makes it nasty is that the error is consistent. The robot is not twitching or behaving randomly. It reliably goes 90 degrees off from what the driver asked, which feels like a driving problem rather than a setup problem. Teams give the driver a re-zero button for exactly this reason.

Verify for current season

Which gyro or inertial measurement unit a team runs, and the API for reading its heading and zeroing it, are both hardware and vendor specific. This lesson deliberately names no device and shows no code, because getting that wrong is worse than leaving it out. Check what is actually mounted on your robot and read that vendor's current documentation.

7 Why there is no code in this lesson

Two reasons, and both are worth being explicit about.

  • You will not write this maths. Swerve kinematics involves real trigonometry per module, and teams use a generator to produce the code. Our curriculum says the same thing: students rarely write swerve from scratch.
  • Neither of our sources verifies a swerve API. Showing you an invented drive(x, y, rot) signature would be exactly the kind of made-up API this course refuses to print. Every code block in this track is either verified or flagged, and there is nothing here to verify.

The point of this lesson is understanding the behaviour. The point of the next one is knowing which generator matches your hardware and what it produces.

9 Common mistakes

Watch out for these
  • Thinking field-centric means the robot always faces forward. The robot can face any direction it likes. Field-centric is about which way it translates, not which way it points.
  • Thinking you have to turn before you can drive that way. That is a car. A swerve translates in any direction instantly, without changing its heading.
  • Thinking the right stick changes the direction of travel. It rotates the body. Translation is unaffected, and that decoupling is the whole reason swerve is worth the complexity.
  • Thinking swerve is four independently driven wheels. Each wheel is also steered by its own motor. Eight motors, not four.
  • Thinking the gyro is set up once and then fine. It has to be zeroed facing a known direction, and drivers need a re-zero button.
  • Planning to write the kinematics yourself. Almost nobody does, and the next lesson is about choosing a generator.
Build it · PenguinBot

Predict the robot on paper

PenguinBot can score from one button press and cannot move across the field. Before you generate a drivetrain, be able to predict what it will do. This exercise is pencil and paper on purpose.

  1. Draw the field top-down with PenguinBot facing east, halfway down one side.
  2. For each input below, draw where the robot goes and which way it faces afterwards. Assume field-centric with the gyro correctly zeroed.
    a. Left stick fully north.
    b. Left stick fully north and right stick left.
    c. Left stick north-west.
    d. Right stick only.
  3. Redo (a) with robot-centric on.
  4. Redo (a) with the gyro zeroed 90 degrees wrong.
  5. Write the drivetrain's entry in PenguinBot's CAN map, all eight motors, grouped so an error message identifies a location.
Reveal the solution

2a. The robot slides north, still facing east. Its body never rotates.

2b. The robot travels north while spinning anticlockwise. Its path is a straight line north and its heading changes continuously. Both at the same time, which is precisely what a tank drive cannot do.

2c. The robot slides north-west, still facing east. All four wheels point north-west.

2d. The robot spins in place and does not translate. The four wheels splay out tangentially.

3. Robot-centric. The robot drives east, the way it is facing, because the stick is now interpreted relative to the robot's nose.

4. Gyro 90 degrees wrong. The robot goes east or west, depending on the sign of the error, when the driver asked for north. Every input is rotated by the same offset, consistently, which is exactly what makes it feel like a driving problem rather than a setup problem.

5. Drivetrain CAN map

CAN IDModuleMotor
10 / 11 / 12 / 13FL / FR / BL / BRdrive
14 / 15 / 16 / 17FL / FR / BL / BRsteer

Grouped this way, an error reading CAN ID 16 timed out means back-left steering with no map and no asking anybody. That is what the ID scheme from Unit 2 is for, and you will be very glad of it in Unit 12.
