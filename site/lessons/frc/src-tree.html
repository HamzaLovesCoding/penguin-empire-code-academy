1 Why this matters

The source curriculum calls Unit 3 the single most important conceptual unit, because everything after it hangs on knowing where things go.

The duplicated ExampleSubsystem

The normal way to make your first subsystem is to copy the ExampleSubsystem the template gave you and rename it. The team did exactly that on the ChairBot. They renamed the file to DrivetrainSubsystem.java, and the editor filled with red squiggles, because the class inside still said ExampleSubsystem. Java requires a public class to match its file name.

Here is the part worth knowing. On some laptops in the room, the editor's rename tool fixed the class declaration automatically. On the older laptops it did not. The same instructions produced two different experiences three feet apart, and the fix took thirty seconds once somebody said it out loud.

Red and yellow are not the same

Red means it will not compile. Yellow is a warning, usually something declared and not used yet, and the project still builds. New members treat both as catastrophes and lose time to the yellow ones.

4 What to ignore

The project contains Gradle files, a wrapper, build output, and test scaffolding. None of it needs to make sense to you this season. The framework exists so you can ignore the build machinery, so skipping it is fine.

Two rules that keep this true:

  • Do not edit files you did not create and were not told to edit. If a fix requires touching build.gradle, that is a conversation with a mentor, not a solo experiment.
  • Do not delete anything to make an error go away. Errors are information.

5 Class names and file names

This is the rule the war story is about, and it comes straight from Java rather than from WPILib.

ArmSubsystem.javaJava
// the file is called ArmSubsystem.java, so the public class must be too
public class ArmSubsystem extends SubsystemBase {

}

If the file says ArmSubsystem.java and the class says ExampleSubsystem, nothing compiles and the error message points at the class declaration. The routine for making a new subsystem is therefore five steps, and the third one is the one people skip:

  1. Copy ExampleSubsystem.java.
  2. Rename the file to ArmSubsystem.java.
  3. Rename the class inside it to ArmSubsystem.
  4. Fix any remaining red references to the old name.
  5. Build and confirm it compiles before writing anything new.

7 Common mistakes

Watch out for these
  • Trying to understand every file before starting. You will touch six things. Everything else is build machinery you can ignore for a year.
  • Assuming Robot.java is where your code goes. It is named after the robot and it holds the mode lifecycle. Your code goes in subsystems, commands, and RobotContainer.
  • Panicking at yellow squiggles. Yellow is a warning. Red stops the build.
  • Assuming renaming a file renames the class. Only if your editor does it for you, and not every setup does. Check the class declaration by hand.
  • Treating Constants.java as optional tidiness. It is for the day a port number changes and it is referenced in four files. Unit 7 has that story.

Map PenguinBot's project

You generated the PenguinBot project in Unit 2 and installed REVLib into it. You have never opened its folders. Do that now, and write the map you will build against.

  1. Navigate to src, then main, java, frc, robot. List what is actually there.
  2. Write one sentence per file: what it is for, and whether you will be editing it.
  3. Write the target tree, the files that will exist when PenguinBot is finished. PenguinBot has an intake, an arm, a swerve drivetrain, and a Limelight.
  4. Name one file you are confident you will never open all season, and say why that is fine.
Reveal the reference map

What is there now: Main.java which you never touch, Robot.java for the mode lifecycle which you rarely touch, RobotContainer.java for bindings and autonomous which you edit constantly, Constants.java for numbers which you edit constantly, and the two example files in subsystems/ and commands/ which exist to be copied.

The target tree:

src/main/java/frc/robot/
├── Robot.java                  Unit 8, mostly untouched

├── Constants.java              Unit 7, IDs, speeds, setpoints, PID gains
├── subsystems/
│   ├── IntakeSubsystem.java    Unit 7
│   ├── ArmSubsystem.java       Unit 7
│   ├── DriveSubsystem.java     Unit 9

    ├── ArmToScoreCommand.java  Unit 7
    ├── AimAtTagCommand.java    Unit 10
    └── ScoreSequence.java      Unit 8

Never opening: Main.java. It exists to start the robot program and there is nothing in it you can usefully change. Not understanding it costs you nothing, which is what a good framework is for.
