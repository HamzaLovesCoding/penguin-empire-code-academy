1 Why this matters

CAN ID 16 timed out

At competition, the programmer's job during a match is to watch the Driver Station console. The line that appears most often is this one:

Driver Station console
ERROR  CAN ID 16 timed out

It means a device stopped answering. Two things cause it: a wrong ID, or a wiring break. The team's experience is that a wiring break is the more common of the two. You get about ninety seconds between matches to work out which one you are looking at.

On PenguinBot, CAN ID 16 is the back left swerve steering motor. By Unit 9 you will have written code for it. The number is not trivia. It is a location.

2 Why an address is needed at all

From Unit 1: CAN is one shared loop and every device sits on the same pair of wires. When the roboRIO sends "run at 70 percent," that message physically reaches every device on the bus. Only one of them should act on it.

The CAN ID is what makes that possible. Each message carries a device number, and each device ignores everything not addressed to it.

WPILib's addressing scheme gives the device number six bits, so the valid range is 0 to 63. Devices ship with a default ID, which means two brand new controllers on the same bus are guaranteed to collide until you change one.

3 Two places, one number

This is where people lose hours. A CAN ID exists in two separate places and nothing checks that they agree.

IN THE CLIENT IN YOUR CODE the device is TOLD your program ASKS its ID, over USB-C to talk to that ID REV Hardware Client new SparkMax(2, ...) CAN ID: 2 these two must match, and nothing enforces it

If the device is set to 5 and your code says 2, the project builds and deploys with no complaint at all. The compiler has no idea what is bolted to the robot. The only symptom is a motor that does nothing, possibly with a timeout in the console.

4 A numbering scheme that pays off

Any set of unique numbers works. A grouped set of unique numbers turns an error message into a location, which is worth a lot at 11pm before a competition.

Team 2551's convention:

  • 0 is the roboRIO and 1 is the PDH. Motors start at 2. This is a practical convention rather than a rule in any manual, so confirm the reserved IDs for your own setup.
  • Group by mechanism. Mechanism motors in the low numbers, drivetrain motors in blocks of four.
  • Leave gaps. Room for the motor you will add in Unit 7 is cheaper than renumbering everything.

5 Assign the map yourself

Give every device below an ID. The checker enforces the rules rather than one answer: unique numbers, nothing on a reserved ID, and everything inside 0 to 63.

Try deliberately breaking it. Put two devices on the same number, or put something on ID 1, and read what comes back. Those two mistakes account for most CAN problems a rookie team has.

6 Reading the timeout error

Now the diagnosis. The message names a device that stopped answering, and the context around it tells you which cause you have.

CAN ID
The unique number identifying one device on the shared bus. Valid values are 0 to 63.
reserved ID
A number the team keeps for a specific device. On this team, 0 for the roboRIO and 1 for the PDH.
ID collision
Two devices sharing a number. Produces intermittent and confusing behaviour rather than a clean error.
timeout
The roboRIO stopped hearing from a device. Usually wiring, sometimes an ID.

8 Common mistakes

Watch out for these
  • Expecting IDs to be assigned automatically. You assign them in the vendor client. Devices ship on a default, and defaults collide.
  • Thinking the ID is set in the code. The code requests an ID. The device is told its ID in the client. Two places, and they can disagree silently.
  • Reading a timeout as a broken motor. It means the device stopped answering the bus. More often than not that is a wire.
  • Using ID 0. On this team 0 is the roboRIO and 1 is the PDH. Start at 2 and confirm the reserved IDs for your own setup.
  • Thinking any unique numbers are as good as any others. Unique is the requirement. Grouped by mechanism is what turns an error message into a location.
  • Not writing the map down. A map that lives in one person's head is a map that stops existing when they are at lunch.
Build it · PenguinBot

PenguinBot's CAN ID map

You have a project with REVLib installed and you know which tool sets a device ID. Time to commit to the numbers the rest of this course uses.

  1. Write the definitive map. Honour the reserved IDs and give every device a number.
  2. Group by mechanism so a number identifies a location on the robot.
  3. Leave room for the arm follower motor you will add in Unit 7.
  4. Finish with one sentence stating what to do whenever a controller gets replaced.

The rule: any time a motor controller is replaced, set its CAN ID before it goes back on the robot. A factory default device on a live bus is an intermittent bug that will cost you a day.

Tape this map inside the electronics bay and keep a copy in the repository. When the console says CAN ID 16 timed out you want to read "back left steering" off it in two seconds, rather than asking who remembers.
