1 Why this matters

The captain's laptop died

Halfway through one season the team captain's personal computer broke. He spent the rest of the year writing robot code on the driver station laptop, the same Windows machine that goes to the field. The robot never noticed and neither did the code.

New members worry they do not have a good enough machine for this. WPILib's VS Code, Gradle, and a deploy over Wi-Fi run on ordinary hardware. What you need is a laptop that turns on.

A second expectation to set. One season the team tried to get robot code simulation working so software could make progress before the robot was built. It never became reliable, so they went back to waiting for real hardware. Tooling does not always cooperate, and that is not a reflection of your ability.

2 WPILib installs its own VS Code

This trips up a lot of people in Unit 2. WPILib is not an extension you add to a copy of VS Code you already have. WPILib's own documentation puts it plainly:

From the WPILib installation guide

"WPILib installs a separate version of VS Code. It does not use an already existing installation. Each year has it's own copy of the tools appended with the year."

So after installing you will have two VS Code applications, and only one of them knows what a robot is. Open the one named for this season. A student who opens their normal VS Code and cannot find the WPILib commands has not broken anything. They are in the wrong application.

The installer brings more than the editor. It carries Gradle, a Java JDK, and the dashboards you meet later in this unit, including Glass, Elastic, and AdvantageScope. You do not install Java separately.

Unlike Game Tools, WPILib itself is cross platform. Its stated requirements are Windows 10 or 11 (64 bit), Ubuntu 22.04 or 24.04 (64 bit), and macOS 13.3 or higher on both Intel and Arm. So a Mac can write and deploy robot code. It still cannot enable the robot.

3 The WPILib commands

Every FRC action lives in one place. You can reach it three ways:

  • The command palette, with Ctrl+Shift+P on Windows or Cmd+Shift+P on macOS, then typing WPILib.
  • The WPILib icon in the top right of the editor window, which the team calls the red W.
  • Right clicking build.gradle, which offers the build and deploy actions directly.
The W icon is missing

Two causes, in order of likelihood. First, you are in your normal VS Code rather than the WPILib copy. Second, you have no file open, so there is no editor for the icon to attach to. Open any file in the project and look again.

Generate the project, open it, and then wait. The first Gradle build takes a while and downloads dependencies. Waiting for it to finish is a real step, not a formality. Editing files while it is running is how people end up with confusing errors on a project they have not written anything in.

5 Command based or timed

Two templates matter for a beginner.

Timed robot
Gives you one method per mode and expects you to write the logic yourself. Simpler to read on day one and more limiting once a robot has several mechanisms.
Command robot
The command based framework. Behaviours are objects with a defined end, mechanisms are subsystems that own their hardware, and buttons are bound to behaviours. This is what Team 2551 uses.

Choose Command Robot deliberately rather than accepting a default. Unit 3 maps the files it generates and Unit 7 teaches what they are for.

6 Build and deploy

Two commands, and the difference between them matters.

CommandWhat it doesNeeds a robot?
Build Robot CodeCompiles your project locallyNo
Deploy Robot CodeBuilds if needed, then copies the program to the roboRIO and starts itYes

WPILib describes a successful deploy as printing "Build Successful" and then opening the RioLog, which shows console output from the running robot program. That is the same output stream you saw in the Driver Station's Messages tab last lesson.

Never power off during a deploy

WPILib's warning is worth repeating exactly: "Avoid powering off the robot while deploying robot code. Interrupting the deployment process can corrupt the roboRIO filesystem and prevent your code from working until the roboRIO is re-imaged."

The practical consequence of the build and deploy split: a build failure is a code problem, and a deploy failure on code that builds is almost always a connection problem. Check Communications on the Driver Station before you touch a line of Java.

Verify for current season

Everything about the install moves between seasons: the download location, the installer steps, where the WPILib icon sits, the exact wording of the palette commands, and the list of project templates. Follow the current season's WPILib documentation rather than a screenshot from last year.

8 Common mistakes

Watch out for these
  • Adding a WPILib extension to your existing VS Code. WPILib ships its own copy, already set up. Open that one.
  • Ticking desktop support because it sounds useful. It is for simulation and unit testing. Leave it off.
  • Treating yellow squiggles as errors. Red stops the build. Yellow is a warning, usually something declared and not used yet, and the project still builds and deploys.
  • Reading a failed deploy as a code problem. If it builds and will not deploy, look at Communications on the Driver Station.
  • Keeping the project in a synced folder. OneDrive and iCloud rewrite files while Gradle is using them, which produces errors that look like nothing you did.
Build it · PenguinBot

Create the PenguinBot project

You know what the hardware is and how to enable the robot. Now make the place all of it will live. This is a real task on your own machine. Your ticks are saved, so you can come back to it.

  1. Open the WPILib copy of VS Code, not your normal one.
  2. Run Create a new project from the command palette.
  3. Choose Template, then Java, then Command Robot.
  4. Pick a local folder that is not synced, and name the project PenguinBot.
  5. Enter team number 2551. Leave desktop support off. Generate the project.
  6. Open the project and wait for the first Gradle build to finish.
  7. Run Build Robot Code and confirm it succeeds with zero changes from you.
  8. Write down the files and folders you see under src/main/java/frc/robot.
What you should end up with

A PenguinBot folder holding a Gradle project. Under src/main/java/frc/robot you will find Main.java, Robot.java, RobotContainer.java, Constants.java, and the folders subsystems/ and commands/ with example files in them.

Build Robot Code reports success. You have not written a line and the project already compiles. That baseline matters: if a build fails later, you changed something, and you know what.

If you cannot do this yet, because you have no Windows machine or no install, keep reading anyway. Unit 3 maps every one of those files, and everything from Unit 4 onward can be practised in this site's sandboxes without a robot.
