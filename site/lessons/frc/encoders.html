1 Why this matters

Two ordinary jobs you cannot do yet

After Unit 4 you can spin a motor. Now try to write these:

  • Shoot once the flywheel reaches 4000 RPM.
  • Raise the arm to the scoring position and stop there.

Neither is possible. motor.set(0.7) is you pushing. It tells you nothing about what happened. The motor could be spinning at 3000 RPM, or stalled against a game piece, or spinning freely because the belt snapped. set(0.7) looks identical in all three cases.

An encoder turns "I pushed" into "here is what happened." Everything in Units 6, 10 and 11 sits on top of it.

2 What an encoder is

An encoder is a sensor that reports how far a shaft has turned and how fast it is turning. Two readings, and the whole rest of this course uses one or the other.

You almost certainly already have one. A SparkMax driving a Neo reads that Neo's built in encoder, and a Kraken has one inside it. You can also clamp a separate encoder onto a shaft, which the next lesson gets into.

The Neo's encoder is not optional

REV's documentation is direct about this: running a brushless motor like a Neo without its integrated encoder plugged into the SparkMax's encoder port can damage the motor. The controller uses that feedback to know how to switch the motor. This is an electrical detail rather than a software one, and it is worth knowing when a mechanism behaves strangely.

3 Reading it in code

Two calls. One to reach the encoder, one to ask it a question.

Verified syntax · REVLib
Arm.javaJava
import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;

SparkMax armPivot = new SparkMax(3, MotorType.kBrushless);

double pos = armPivot.getEncoder().getPosition();   // rotations
double vel = armPivot.getEncoder().getVelocity();   // RPM

getEncoder() hands you a RelativeEncoder, which is the built in one. Then getPosition() and getVelocity() ask it for numbers. You can hold onto the encoder in a field instead of calling getEncoder() twice, and both styles are common.

4 What the numbers mean

This is where people get burned, so read the table rather than guessing.

CallDefault unitMeans
getPosition()RotationsHow far the motor shaft has turned, counted from wherever the encoder was last zeroed
getVelocity()RPMHow fast the motor shaft is turning right now
motor.get()Percent outputWhat you asked for. Not a measurement at all

Three consequences worth stating plainly:

  • It is the motor shaft, not the mechanism. If a 10 to 1 gearbox sits between the motor and the arm, ten motor rotations move the arm through one output rotation.
  • It is signed. Run the motor the other way and position goes negative. Position is a count, not a distance.
  • Zero is wherever it was last zeroed. Position 9.0 does not mean the arm is up. It means the shaft is 9 rotations from a reference you have to know about, and that reference is the next lesson.

REVLib can convert the units for you. A configuration object carries a positionConversionFactor and a velocityConversionFactor, which multiply the raw reading. Setting the position factor to 360 gives degrees, and setting it to 0.1 gives output rotations through a 10 to 1 gearbox. The two factors are independent, so changing one does not change the other. This course leaves both at their defaults and works in rotations and RPM throughout.

Verify for current season

How you apply configuration to a SPARK has changed across REVLib versions. Current REVLib uses a configuration object applied with configure(), and older code sets parameters directly on the motor. The default units above have been rotations and RPM throughout, and the way you change them has not. Check REV's current documentation before writing a conversion factor.

6 Why velocity ramps

Look at the velocity column again. It climbs fast at first, then flattens: 14.17, then 21.64, then 25.59, then 27.67, then 28.77. It is approaching a ceiling and never quite arriving.

This is not the encoder being slow. The encoder reports faithfully. It is the mechanism taking time to get up to speed, because it has mass.

That single fact is why the flywheel from Unit 3 needs a command with an end. If you check the velocity on the first cycle after commanding full power, you get a number near zero, and a naive check would conclude the flywheel is broken. Something has to keep asking until the answer is yes. That something is isFinished().

encoder
A sensor reporting how far a shaft has turned and how fast it is turning.
getEncoder()
The call that hands you the SparkMax's built in encoder.
position
Rotations of the motor shaft, counted from the last zero. Signed.
velocity
Motor shaft speed in RPM. What you check when readiness matters.
conversion factor
A multiplier that turns raw rotations or RPM into the units you would rather work in.

8 Common mistakes

Watch out for these
  • Using motor.get() as a speed reading. It returns what you asked for. Only the encoder tells you what actually happened, and that is why you need a sensor.
  • Assuming position is in degrees. Motor rotations by default, through whatever gearbox sits between the motor and the mechanism.
  • Thinking you need to buy an encoder. Your SparkMax and your Kraken already have one. It is a method call away.
  • Expecting velocity to hit its target immediately. It ramps, because a real mechanism has mass. This is why "wait until up to speed" has to be a behaviour with an end.
  • Reading position 0 as "the arm is down." Position 0 means wherever the encoder was last zeroed. The next lesson is entirely about that.

An arm that knows where it is

PenguinBot has an Intake class from Unit 4 with intake(), stop() and outtake(), and no idea what any mechanism is doing. Give it an arm that can answer questions.

Write an Arm class. It is a plain class for now and becomes a real Subsystem in Unit 7.

  1. A SparkMax on CAN ID 3, brushless, from the map you wrote in Unit 2.
  2. setSpeed(double speed) to move the arm, and stop().
  3. getPosition() returning the arm's position in rotations.
  4. getVelocity() returning the arm's velocity in RPM.
  5. printStatus() printing one formatted line with both readings.
  6. Bonus. Make setSpeed refuse anything above 0.8 in magnitude, so the arm can never be commanded past the team's limit no matter who calls it.

Write it in the sandbox below. The main method is already there to exercise your class.

Reveal the solution
Arm.java · solutionJava
import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;

public class Arm {
    // CAN ID 3, PenguinBot's arm pivot, from the map in Unit 2
    private final SparkMax pivot = new SparkMax(3, MotorType.kBrushless);

    public void setSpeed(double speed) {
        // Bonus: never exceed the team's 80% rule, whatever the caller asks for
        double safe = Math.max(-0.8, Math.min(0.8, speed));
        pivot.set(safe);
    }

    public void stop() {
        pivot.set(0);
    }

    public double getPosition() {
        return pivot.getEncoder().getPosition();   // rotations
    }

    public double getVelocity() {
        return pivot.getEncoder().getVelocity();   // RPM
    }

    public void printStatus() {
        System.out.printf("arm: %8.2f pos   %8.2f vel%n", getPosition(), getVelocity());
    }
}

Three things in that solution are worth more than the syntax:

  • The motor is private final. Nothing outside Arm can reach it. That is the ownership rule from Unit 3, enforced by Java's own access modifiers rather than by everyone remembering.
  • The clamp in setSpeed turns the 80 percent rule from something you remember into something the code guarantees. You will use this exact clamp again in Unit 6, where a PID controller will cheerfully ask for 1.8.
  • getPosition() returns raw rotations on purpose. PenguinBot's setpoints are in rotations all the way through this course.

The arm can now tell you it is at 9.00 rotations. But 9.00 rotations from where? Restart the robot and find out. That is the next lesson.
